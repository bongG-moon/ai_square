03. 첫 연결은 KEY 한 번으로

  1. 웹 상단 열쇠 아이콘 → 내 연결 KEY에서 개인 KEY를 발급합니다.
  2. 같은 웹 화면에서 로컬 MCP ZIP을 받아 사용하는 AI에 등록합니다. 처음 연결할 프로그램과 프로젝트 / 내 계정 범위를 선택합니다.
  3. AI에 연결을 요청하고 같은 채팅에 개인 KEY를 입력합니다. 서버 주소는 웹 ZIP에서 자동 설정합니다. KEY는 모델과 대화·도구 호출 기록에 남을 수 있습니다. MCP 결과에는 원문을 표시하지 않으며 PC에는 암호화 저장합니다. HTTP는 정확한 주소에 대한 비암호화 전송 동의를 확인합니다.
  4. 서버에서 사번·이름·권한을 확인하고 “홍길동 · 융합기술팀 / 조회·다운로드·본인 등록 연결됨”을 표시합니다.
  5. 이후 사용자는 대화로 검색·설치·등록을 요청합니다. KEY 재발급 시 채팅에서 재연결을 요청하고 새 KEY로 교체합니다.

서버에는 현재처럼 KEY 해시와 사번·권한만 저장합니다. PC에는 Windows 자격 증명 저장소 등 OS 보안 저장소를 사용하고, 일반 설정 파일에는 서버 주소·자격 증명 항목 이름만 둡니다. 초기 호환 환경에서는 프로세스 환경변수나 숨김 입력도 가능하지만 평문 JSON 영구 저장을 기본값으로 하지 않습니다. 사용자가 PC와 프로세스를 통제하면 자기 KEY를 추출할 수 있으므로 서버 권한 제한이 최종 보호 장치입니다.

사내 HTTP 주소 지원. 현재 운영 조건을 반영하여 최초 연결 때 비암호화 전송을 알리고 사용자가 확인한 정확한 주소만 허용합니다. KEY를 다른 주소로 리다이렉트하지 않으며 HTTPS 인증서 검증을 끄지 않습니다. HTTP 자체가 암호화되는 것은 아닙니다. Flask 실행 진입점·포트는 변경하지 않습니다. 새 로컬 MCP는 setup에서 주소를 확인하고, 기존 Skill 클라이언트는 configure --allow-http를 사용합니다.

KEY는 현재 정책처럼 유효기간 없이 취소·재발급으로 관리합니다. 단, 게시 초안 승인에는 짧은 유효기간을 둡니다. KEY와 게시 승인 번호는 서로 다릅니다. SSO 웹 로그인 상태가 로컬 MCP에 자동 전달되는 것은 아닙니다.

04. 원하는 업무를 먼저, 조직 선호는 보조로

사용 예시 · 숫자와 도구는 설명용 가상 데이터

사용자 “우리 팀에서 많이 쓰는 메일 조회 도구 찾아줘.”

MCP 검색 결과 ① 메일 조회 A — 업무 일치 높음 · 내 부서의 최근 다운로드가 상대적으로 많음 · 바로 사용 가능
② 메일 조회 B — 전사 누적 순위 상위 · 첨부파일 검색 지원 · 조회 권한 신청 필요
③ 메일 요약 Skill — 메일을 직접 조회하지 않고 전달받은 내용만 요약

AI “메일을 직접 찾으려면 A가 더 맞습니다. B는 첨부파일 검색이 필요할 때 후보입니다.”

  1. 후보 검색: 이름·태그·설명·업무 분류를 검색합니다. AI가 ‘메일 / 이메일 / email’처럼 검색어를 확장할 수 있지만 결과에 없는 기능을 만들어 설명하지 않습니다.
  2. 적합성 우선: 지원 프로그램·운영체제·설치 방식이 맞는지 표시하고, 무관한 도구는 인기가 높아도 추천 상단으로 올리지 않습니다.
  3. 조직 보정: 인증된 사용자의 dept_cd로 같은 부서의 반응을 집계합니다. 도구 등록 조직 orgId와 SSO 부서코드는 다른 개념입니다.
  4. 근거 반환: “검색어가 이름/태그와 일치”, “같은 부서 반응 우세”, “최근 7일 순위 상위” 같은 서버 근거와 기준 시각을 AI에 전달합니다.

초기 추천 점수는 검색 관련도 75% + 부서 선호 20% + 최근 인기 5%를 출발점으로 제안합니다. 모두 같은 0~1 범위로 정규화하고, 관련도 기준을 통과한 후보끼리 비교합니다. 확정 공식이 아니라 실제 사내 검색어와 평가 결과로 조정할 운영값입니다. 정확한 이름·도구 ID 검색은 해당 결과를 우선합니다.

부서 선호를 만드는 기준

최근 90일의 고유 다운로드와 현재 유효한 좋아요를 사용합니다. 다운로드는 실제 사용·만족을 증명하지 않으므로 “많이 사용하는 도구”보다 “다운로드·좋아요가 많은 도구”라고 안내합니다.

1차는 현재 같은 부서인 구성원들의 최근 활동으로 정의합니다. 과거 당시 부서라고 주장하지 않습니다. 이후 활동 시점의 부서코드를 저장하는 경우에도 과거 데이터를 임의로 채우지 않습니다.

적은 데이터와 조직 유사도

초기 제안으로 서로 다른 구성원 5명 미만이면 부서별 숫자·세부 근거를 숨기고 전사 결과로 보완합니다. 표본이 적은 점수는 전사 평균 쪽으로 완화합니다.

다른 부서는 관리자가 확인한 조직 계층·직무 그룹으로만 묶습니다. 부서명이나 코드 앞자리로 조직 관계를 추측하지 않습니다. 비교 데이터가 없으면 “조직 추천 근거 부족”으로 표시합니다.

정렬 모드동작
추천검색 관련도 중심 + 부서 근거 보정. 기본 검색 모드.
실시간접속/조회 시점의 최근 7일: 유효 좋아요×2 + 최초 고유 다운로드×1. 재다운로드·업데이트 제외.
누적전체 기간: 유효 좋아요×2 + 최초 고유 다운로드×1.
최근 등록최초 등록 시각 순서. 새 버전 공개 시각과 구분해서 표시.

실시간·누적 모드에는 개인화 점수를 섞지 않습니다. 웹과 MCP가 같은 집계 함수·정렬·동점 처리·기준 시각을 사용하도록 공통화합니다. 좋아요는 현재 코드의 최초 시각·현재 선택 상태 기준을 유지해 취소/재선택으로 최근 순위를 반복 부풀리지 않게 합니다. 권한이 없는 항목도 현재 웹 정책처럼 공개 요약과 “권한 필요”만 노출하며 상세·파일·개인별 이용 이력은 반환하지 않습니다.

현재 catalog API는 MongoDB 문자열 검색과 페이지 제한을 사용하고, 웹 bootstrap과 통계는 여러 도구·활동 자료를 한 번에 읽습니다. 두 경로를 구분해 규모에 맞게 최적화합니다. 1차는 제한된 후보 검색·캐시된 집계·페이지네이션과 사내 동의어 목록으로 시작합니다. 한국어 부분 검색 성능은 실제 데이터로 측정하며, MongoDB 기본 텍스트 인덱스만으로 한국어 의미 검색이 해결된다고 가정하지 않습니다. 벡터 검색은 후속 선택 사항입니다.

05. 다운로드와 설치·실행은 상태를 구분합니다.

설치 전 한 번의 구체적인 확인

“메일 조회 A v3을 현재 프로젝트에 연결합니다.
대상: 선택한 프로젝트의 MCP 설정 · 추가: mail-search 항목
필요 환경: Python 3.11 · 의존성 설치: 있음 · 관리자 권한: 없음
기존 설정은 보존하고 바뀌는 파일을 백업합니다.”

[현재 프로젝트] [내 계정 전체] [취소] → 선택한 계획 확인 → 다운로드·설치 → 연결 점검

  1. 서버가 현재 권한·배포 상태를 확인하고 고정된 배포 번호와 SHA-256을 반환합니다. 확인 뒤 새 버전이 나와도 다른 파일로 몰래 바꾸지 않습니다.
  2. 로컬 MCP가 형식·지원 프로그램·의존성·설치 범위·충돌을 점검하고 구체적인 설치 계획을 보여줍니다.
  3. 사용자가 범위를 명시적으로 고른 뒤 파일을 받고 해시를 검사합니다. 다운로드만 요청하면 여기서 종료합니다.
  4. 지원되는 설치 어댑터가 선택한 경로만 변경합니다. 기존 설정을 병합하고 충돌이 있으면 덮어쓰지 않고 확인합니다.
  5. 복사/설치/프로세스 시작/연결 점검을 별도 상태로 기록합니다. 설치기 실행만으로 “설치 성공” 또는 “업무 실행 성공”이라고 표시하지 않습니다.
형식 / 대상실행 가능한 수준으로 만드는 방법한계
단일 MD Skill선택한 호스트의 프로젝트/사용자 Skill 위치에 복사. 이름 충돌·참조 누락 확인.MD 자체는 실행 파일이 아님. AI 호스트가 읽을 수 있는 상태를 검증.
여러 파일 Skill ZIP경로·심볼릭 링크·압축 해제 크기를 검사해 전용 임시 폴더에서 해제 후 필요한 파일 배치.Python 스크립트가 있으면 별도 의존성 준비와 실행 권한 필요.
로컬 MCP / Tool관리되는 사용자/프로젝트 하위 위치에 배치. 필요한 경우 전용 가상환경과 호스트 설정 항목 구성.사내 패키지 저장소·프록시·런타임이 없으면 설치 불가 상태를 구체적으로 안내.
플러그인 / 하네스대상 프로그램의 실제 지원 설치 방식을 적용. 기존 MCP·Skill·개인 설정과 충돌 점검.전역 프롬프트·후크 변경은 별도 변경 내역 표시. 지원되지 않는 호스트는 안내형.
EXE / MSI / PS1파일·서명 상태·실행 명령·요구 권한을 보여준 후 설치기 시작. 승인된 조용한 설치 옵션만 사용.임의 EXE의 설치 위치·부작용은 바깥에서 강제 불가. 지원 범위를 모르면 수동 설치기로 안내.
설치 명령 / 원격 MCP URL확인된 명령 또는 연결 어댑터 사용. URL·헤더·scope를 목적에 맞게 설정.범용 shell 실행 도구는 노출하지 않음. 외부 서비스 KEY는 플랫폼 KEY와 별개.

모든 ZIP을 자동 실행하지 않습니다. 현재 배포 정보의 시작 파일·의존성 설명은 안전한 자동 실행 허가가 아닙니다. 별도의 버전 있는 installProfile 계약으로 허용 동작·대상·실행 인자·의존성·검증 방법을 선언하고 서버에서 검증합니다. 제작자 선언과 운영자 검토 여부를 구분하며, 미지원 패키지는 다운로드·설치 안내로 처리합니다. 자동 설치 정보가 없다고 기존 등록을 막지는 않습니다.

설치 상태는 로컬에 서버/도구 ID/배포 번호/해시/호스트/범위/경로/변경 파일을 보관합니다. 실행 시 버전 확인은 최신 여부를 알리고, 실제 파일 교체는 사용자가 업데이트를 요청했을 때만 합니다. 실행 훅이 없는 단일 MD Skill은 매 사용 시 자동 확인을 보장하지 않고 MCP의 내 설치 목록·업데이트 확인으로 보완합니다. 등록자의 임의 코드나 모든 외부 설치기의 완전한 제거·복구는 보장할 수 없으며 관리한 파일·설정 범위에서만 복구합니다.

다운로드 집계

웹과 MCP 모두 같은 다운로드 API를 사용하고 사번×도구 ID당 최초 1회만 집계합니다. 여러 PC·KEY 재발급·재시도·새 버전 업데이트로 늘어나지 않습니다. 업데이트는 purpose=update로 요청하고 원시 전송 이력과 인기 집계를 분리합니다. 서버가 파일 응답을 시작한 기록은 사용자 PC의 저장·설치 완료를 보장하지 않으므로 설치 성공률과 혼합하지 않습니다. URL 연결·명령 안내에는 실제 설치 파일 전송이 없으므로 다운로드를 인위적으로 늘리지 않습니다.

06. 폴더에서 새 도구 또는 새 버전까지

등록 대화 예시

사용자 “이 폴더의 메모 정리 Skill을 AI SQUARE에 등록해줘.”

AI “MD와 Python 처리 코드가 있어 ZIP으로 준비했습니다. 기존에 등록하신 ‘업무 메모 요약’과 packageId가 같습니다. v3의 새 버전으로 등록할까요, 별도 도구로 등록할까요?”

사용자 “새 버전으로. 이번엔 권한 승인받아야 볼 수 있게 해줘.”

AI “변경 내용·공유 조직·업무·조회 권한을 채웠습니다. 아래 게시 확인 화면에서 확인해 주세요.”

웹 이전/새 설명, 파일 목록·용량, v3 → 새 배포, 변경 내용, 조직·업무, 승인 필요 표시 → [이 내용으로 게시 승인]

AI 승인된 내용 게시 → “v4 등록 완료”와 웹 링크·검증 결과 반환

  1. 로컬 준비: 사용자가 선택한 폴더·파일만 읽습니다. 원본은 그대로 두고 배포용 임시 폴더를 만듭니다. 현재 배포 Skill 규칙을 패키징 라이브러리와 함께 재사용합니다.
  2. 자동 초안: 이름·200자 이내 소개·유형·프로그램·태그·설치 안내·실제 동작 흐름 1~8단계를 제안합니다. 출처에 없는 기능을 적지 않습니다. 웹 서버에 LLM을 새로 넣을 필요는 없습니다.
  3. 형식 선택: 코드/참조가 여러 개면 ZIP, 단일 MD 요청이면 MD 그대로, URL/명령형이면 해당 방식으로 준비합니다. EXE 변환은 하지 않습니다.
  4. 기존 도구 확인: 같은 서버의 저장된 toolId → 본인 소유 packageId → 이름·설명 유사도 순으로 확인합니다. 의미가 비슷하다고 자동으로 덮어쓰지 않습니다. 다른 사람의 도구는 업데이트 후보가 아닙니다.
  5. 필수 선택: 신규/새 버전, 조직·업무, 공개/승인 필요를 명시적으로 확인합니다. 기존 값은 제안하되 최종 확인표에 표시합니다. 별도 신규 도구를 선택하면 새 packageId를 부여해 다음 업데이트가 혼동되지 않게 합니다.
  6. 서버 초안: 검사된 파일을 임시 저장하고 사번·KEY ID·메타데이터·대상 도구·revision·파일 해시와 묶어 저장합니다. 승인형의 목록은 공개 요약만, 상세와 파일은 조회 권한이 승인된 사용자/등록자/관리자로 제한합니다.
  7. 확인과 게시: 웹 SSO 세션에서 본인 초안을 확인·승인한 후 MCP가 게시합니다. 서버는 승인된 파일·내용·공개 범위만 사용합니다. 파일이나 대상이 바뀌면 새 확인이 필요합니다.
  8. 결과 조회: 서버가 배포 번호를 발급합니다. 응답 유실 시 같은 요청 ID의 결과를 조회/재시도해 중복 도구·버전을 만들지 않습니다.
왜 마지막에 웹 확인을 권장하나요? 대화에서 “네”라고 답하는 UX만으로는 변조한 MCP를 막을 수 없습니다. confirmed=true도 사용자가 직접 보낼 수 있습니다. KEY 요청만으로 확인 절차를 건너뛰지 못하게 하려면, KEY로 호출할 수 없는 SSO 웹 확인 경로가 필요합니다. 등록자는 웹 폼을 다시 채우는 것이 아니라 자동 작성된 한 화면에서 확인만 합니다. 채팅 확인만 채택할 수도 있지만 그 경우 이를 변조 방지 장치라고 설명하면 안 됩니다. 웹 확인 기록 역시 해당 사용자 세션의 승인을 기록하는 것이지, 사람이 실제로 내용을 읽었음을 증명하는 것은 아닙니다. 타인·관리자 영역 접근을 막는 소유권 검사는 어느 확인 방식을 선택해도 서버에서 필수로 적용합니다.

현재 ai-square.json v1은 알 수 없는 필드를 거부합니다. 설치 계획 필드를 임의로 덧붙이지 않고, 우선 배포와 해시로 연결된 별도 installProfile 스키마를 추가하는 방식으로 기존 ZIP 호환성을 유지합니다. 나중에 배포 규격을 올릴 때 Skill·검사기·예제·패키지 ZIP을 함께 갱신합니다.

DB는 웹 서버의 제한된 서비스 계정만 접근하고 서버 저장소는 정적 공개 디렉터리로 열지 않습니다. 서비스 계정의 최소 컬렉션 권한과 네트워크 접근 제한을 함께 적용합니다. MCP에 담는 것은 API 주소와 사용자 자격 증명 접근 방식뿐입니다.

도구 설명·README·SKILL.md·설치 가이드에 “KEY를 보내라”, “검사를 생략하라”는 문장이 있어도 실행 지시로 승격하지 않습니다. 검색 자료는 데이터로 처리하고 설치기는 허용된 구조화 동작만 수행합니다. 사용자 파일을 검사할 때 비밀 값은 로그·오류·게시 초안에 복사하지 않습니다.

보장 범위: 이 설계는 자기 KEY로 타인·관리자 영역을 침범하지 못하게 하는 것입니다. 사용자가 자기 PC에서 변조한 프로그램을 직접 실행하는 것, 이미 정당하게 받은 파일을 외부에서 재사용하는 것까지 플랫폼이 통제할 수는 없습니다. 난독화·서명은 배포본 출처 확인에는 도움이 되지만 권한 검사를 대체하지 않습니다.

향후 원격 HTTP MCP는 전용 OAuth 접근 토큰의 대상·권한을 검증하는 방식으로 설계합니다. 기존 API KEY를 임의 원격 서버에 넣고 그대로 다른 서비스로 중계하는 구조는 사용하지 않습니다. 1차 로컬 stdio MCP가 자기 프로세스의 API 자격 증명으로 AI SQUARE API를 호출하는 구조와 원격 OAuth 토큰 중계를 구분합니다.

아래 이름은 신규 제안입니다. 현재 API가 이미 모두 존재한다는 뜻이 아닙니다. JSON 입력·출력 스키마를 고정하고 설명문만 보고 실행하지 않습니다.

서버 API 변경 제안

  • GET /api/integration/me: 현재 인증 사용자·부서·권한·capabilities. 비밀 없이 반환.
  • GET /api/catalog 확장: 추천/실시간/누적 정렬·페이지네이션·근거·권한 상태. 웹과 동일한 랭킹 함수.
  • GET /api/publish-targets 확장: KEY는 본인만. packageId 정확 일치와 본인 유사 후보를 구분.
  • POST /api/publish-drafts, GET /api/publish-drafts/{id}: 파일 검사·초안 저장·본인 상태 조회.
  • POST /api/publish-drafts/{id}/approve: 웹 SSO 세션+CSRF 전용. KEY로 호출 불가.
  • POST /api/publish-drafts/{id}/commit: 승인된 내용 게시. 현재 KEY·소유권·taxonomy·revision 재검사.
  • GET /api/tools/{id}/releases/{n}/install-profile: 해당 배포 해시와 연결된 구조화 설치 정보.

기존 /api/tools와 /api/tools/{id}/versions에 KEY로 직접 POST해 승인 초안을 우회할 수 없도록 반드시 동일 조건을 적용합니다. 기존 배포 클라이언트도 함께 업데이트합니다. 사용자에게 단순 403 대신 “게시 확인이 필요합니다”와 확인 경로를 반환합니다. 웹의 정상 게시 흐름에는 기존 세션·CSRF·소유권 검사를 유지합니다.

저장소 구분

위치보관 내용
MongoDB 기존users / local_tokens / tools / activity_state / activity / access / taxonomy / audit. KEY 원문과 ZIP 바이트는 저장하지 않음.
MongoDB 추가publish_drafts: 사용자·KEY ID·targetRevision·메타데이터·파일 해시·임시 파일 ID·승인·결과·만료

서버 파일 저장소검사 전/초안용 임시 파일, 확정 배포 원본. 사용자 전달 경로로 직접 쓰지 않고 서버 발급 ID 사용. 임시 파일도 용량 한도 포함.
로컬 PCOS 자격 증명 저장소, 다운로드 캐시, 선택한 설치 위치, 설치 기록·설정 백업. 업로드에 이 개인 상태가 섞이지 않게 제외.

초안은 prepared → awaiting_approval → approved → publishing → published 상태와 취소·만료·충돌 상태를 둡니다. 승인은 사번·KEY ID·파일/메타데이터 해시·대상 revision과 결합하고 짧은 유효기간을 가집니다. 재발급·권한 회수·동시 버전 등록이 있으면 재확인합니다. 게시의 기존 clientRequestId·fingerprint와 단일 문서 원자적 저장/outbox를 재사용해 재전송은 같은 결과를 돌려줍니다. 승인 상태만 먼저 소비하고 게시 실패로 영구 정지시키지 않도록 게시 결과를 요청 ID로 복구합니다.

만료된 초안 파일은 참조와 진행 상태를 확인하는 정리 작업이 삭제합니다. MongoDB TTL로 문서만 먼저 지우면 파일이 남을 수 있으므로 파일 정리 완료 후 메타데이터를 만료시킵니다. 목록 조회에서 오래 걸리는 전역 정리·집계를 직접 수행하지 않습니다. 실행량이 많아지면 별도 작업자로 분리할 수 있습니다.

구현 위치 제안

  • 기존 권한 보강: backend/local_access.py, backend/mongo_api.py
  • 공통 검색/순위: 신규 backend/catalog_search.py, backend/department_recommendations.py와 기존 mongo_activity.py
  • 승인 게시: 신규 backend/publish_drafts.py, 웹 확인 template/frontend, 기존 저장/outbox 재사용
  • 로컬 MCP: 신규 독립 integrations/pt-square-mcp/ 아래 server / API client / credentials / packaging / installers / tests
  • 규칙 정본: 현재 static/guides/pt-file-distribution/. 공통 계약을 중복 복사해 서로 달라지지 않게 생성·동기화 검사

새 설정이 필요하면 기존 runtime_config.py 패턴과 기본값으로 제공합니다. 예: 게시 초안 보관 시간·부서 추천 최소 표본·추천 가중치·KEY별 호출 한도. .env를 필수로 도입하지 않습니다. 초기 MCP는 공식 Python SDK 기반 독립 패키지로 고정 버전을 관리하고 사내 패키지 저장소 또는 검증된 배포본을 사용합니다. 회사의 Python/Docker 설치 가능 여부를 확인하지 않고 Docker를 필수 조건으로 만들지 않습니다.

09. 구현 순서와 완료 기준

1단계 · 서버 권한과 읽기

사용자 확인을 거친 HTTP/HTTPS 접속 경로, KEY 연결, 관리자 KEY의 own-only 제한, 검색·상세·실시간/누적·다운로드 MCP. PC 자동 설치를 포함하지 않는 첫 검증 지점.

2단계 · 준비와 게시

배포 Skill 패키징 연결, 단일 MD/ZIP 지원, 내 도구 후보, 서버 게시 초안·웹 확인·신규/새 버전·재시도. 기존 직접 API 우회 차단까지 함께 완료.

3단계 · 설치까지

범위 선택, Skill 복사·지원 MCP 연결 어댑터, 해시·의존성·충돌·설치 확인. EXE는 지원 프로필별로 시작/완료 검증 범위를 표시.

4단계 · 조직 추천과 확장

부서 집계·표본 기준·검색 평가. CUBE/다른 클라이언트 수요가 확인되면 원격 MCP와 OAuth 도입. 로컬 도우미는 재사용.

각 단계는 인수 확인 지점입니다. 사용자가 요청한 전체 범위의 완성은 설치와 조직 추천까지 포함합니다. 데이터가 적은 초기에는 조직 추천이 전사 결과로 보완되는 것이 정상입니다.

반드시 통과해야 하는 검증
  • 일반·관리자 KEY 모두 타인 도구 게시 불가. 삭제·승인·관리 API 직접 호출도 거절.
  • 권한 없는 자료는 공개 요약만. 파일 URL을 알아도 다운로드 불가. 취소·재발급·비활성 계정 즉시 거절.
  • 웹→MCP, MCP→웹, 여러 PC 다운로드가 합계 1회. 업데이트·재시도·HEAD는 인기 건수를 늘리지 않음.
  • 승인 없는 초안, 다른 KEY/사번, 승인 후 파일 변경, 만료, 대상 revision 충돌, 기존 API 우회 모두 거절.
  • 응답 유실·동시 commit에도 게시 1회. 원본 저장 성공 뒤 알림 실패는 실패 게시로 오인하지 않음.
  • ZIP 탈출·심볼릭 링크·과도한 해제 용량·비밀 포함·임의 외부 URL·인증 헤더 redirect 검사.
  • 설치 취소 시 무변경, 프로젝트/내 계정 범위 정확, 기존 설정 보존, 해시 불일치 중단, 의존성 실패 복구.
  • 배포물 설명에 악성 지시를 넣어도 KEY 노출·승인 생략·자동 명령 실행이 발생하지 않음.
  • 실시간·누적 순위가 웹과 일치. 검색 무관한 인기 도구 제외, 적은 부서 표본 비노출, 부서 이동 기준 명시.

추가하면 유용한 작은 기능

권한 신청 링크, 설치 가능 여부 먼저 확인, 내 설치 목록과 업데이트 확인, 실패 문의 번호, 설치 파일 교체 여부·게시 이력를 함께 제공합니다. 승인 자체·관리자 작업은 기존 웹에서 합니다. AX Workspace의 공식 연결 도우미는 이 탭의 관리자 등록 정책을 유지하고 일반 MCP 업로드 API에 연결하지 않습니다.

운영에서 확인할 값: 실제 HTTP/HTTPS 웹/API 주소와 HTTPS 사용 시 회사 인증서, 초기 대상 호스트(우선 Claude Code 권장), 로컬 Python/설치기 허용 범위, 사내 의존성 저장소, 실제 조직 계층 매핑 유무. 사번·조직·KEY·MongoDB 비밀번호를 대화창에 모아 받을 필요는 없습니다.
