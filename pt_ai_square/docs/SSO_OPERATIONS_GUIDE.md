# P&T AI SQUARE · SSO 운영 설정 상세 가이드

**운영 담당자를 위한 문서 · 2026년 10월 23일 · 현재 소스 기준**

회사 SSO가 준비되어 있다는 가정 아래, 플랫폼을 회사 서버에 올리고 실제 사번으로 사용하는 순서입니다. SSO는 회사 로그인을 통해 사용자가 누구인지 확인하는 기능입니다. MongoDB는 등록 정보·권한·이력을 저장하고, 서버 폴더는 업로드한 파일 원본을 보관합니다.

핵심은 **runtime_config.py에 운영 값을 입력하고, 회사 기본 index.py → web_main.py 구조로 실행하는 것**입니다. 회사가 정한 시작 명령과 포트를 임의로 바꾸지 않습니다. 별도 아이디·비밀번호 로그인 화면은 없으며, SSO 코드의 주석을 해제하거나 홈 화면 함수를 새로 붙일 필요도 없습니다.

이 문서는 운영용 값을 실제로 적용하지 않습니다. 현재 로컬 실행 설정을 유지합니다. 회사 hcputil·SSO 서버·프록시를 통과하는 최종 로그인은 실제 운영 주소에서 확인해야 합니다.

**현재 확인된 브라우저 접속 주소는 `http://`입니다. 이 환경에서는 `PTAI_AUTH_MODE = 'sso'`를 유지하고 `PTAI_COOKIE_SECURE = False`를 사용합니다.** 아래 HTTPS 주소와 `True` 설정은 HTTPS 배포 예시입니다. 실제 브라우저 접속을 HTTPS로 전환하면 `True`로 설정합니다. 외부 접속은 HTTPS이고 프록시에서 앱까지의 내부 통신만 HTTP인 경우에도 `True`를 유지합니다.

`PTAI_COOKIE_SECURE`는 브라우저가 앱 세션 쿠키를 전송할 조건입니다. HTTP 접속에서 `True`이면 세션 쿠키가 전송되지 않아 로그인 상태가 유지되지 않습니다. `False`로 설정해도 회사 SSO 인증과 세션 만료·권한 검사는 그대로 적용됩니다.

## 1. 먼저 이해할 운영 구조

```text
직원 브라우저
  → 회사 웹 주소(실제 HTTP 또는 HTTPS) / 회사 SSO
  → 회사 기본 index.py → web_main.py의 app → Flask 플랫폼
       ├─ MongoDB: 사번, 등록 정보, 버전, 권한, 이력, 알림, 인증키 해시
       └─ 서버 저장 폴더: 배포 파일 원본, 기능 요청 첨부파일

직원 PC의 배포 Skill / 다운로드 Skill
  → 같은 HTTPS 웹 주소 + 본인 API 인증키
  → 동일한 Flask API → 동일한 MongoDB / 파일 저장소
```

직원 PC에는 MongoDB 비밀번호를 알려주지 않습니다. 직원은 웹 주소와 자신의 인증키만 사용합니다. 웹 로그인은 회사 SSO, 터미널에서의 호출은 개인 API 인증키가 담당합니다.

| 맡는 사람 | 해야 할 일 | 입력하거나 확인하는 곳 |
|---|---|---|
| 회사 배포·SSO 담당자 | 운영 주소, HTTPS, SSO 등록과 쿠키 전달, 실행 환경 준비 | 회사 배포 설정 및 SSO 관리 체계 |
| MongoDB 담당자 | DB 주소·계정·권한·네트워크 접속 제공 | MongoDB 관리 환경 |
| 플랫폼 운영자 | 설정 파일 작성, 서버 시작, 기본 관리자 지정 | runtime_config.py 및 회사 실행기 |
| 기본 관리자 | 조직·업무, 추가 관리자, 저장 용량 설정 | 웹의 관리자 탭 |
| 일반 직원·등록자 | 로그인, 도구 이용, 등록, 필요한 경우 인증키 발급 | 웹 및 개인 PC의 Skill |

**현재 앱에는 SSO_CLIENT_ID, SSO_CLIENT_SECRET, SSO_LOGIN_URL 같은 설정 항목이 없습니다.** 위 이름을 임의로 추가해도 동작에 반영되지 않습니다. 현재는 회사 SDK가 요청을 받아 쿠키 검증과 이동 주소를 제공하는 방식입니다. 회사 SDK에 별도 설정이 필요하다면 해당 SDK의 회사 설치 지침에 따라 구성합니다.

## 3. 배포할 폴더와 수정할 파일

pt_ai_square 폴더 전체를 운영 서버에 복사합니다. 이름을 바꾸거나 이 폴더 자체를 배포 루트로 사용해도 됩니다. web_main.py 하나만 복사하면 동작하지 않습니다.

```text
pt_ai_square/
  index.py                     회사 기본 시작 파일 / application 제공
  web_main.py                  Flask app 생성 및 기능 연결
  __init__.py                  공용 앱 초기화 / 테스트용 앱 생성
  __main__.py                  선택적인 로컬 보조·관리 명령
  _square_bootstrap.py         상위 폴더 없이 실행하도록 연결
  config.py                   설정을 읽는 코드
  runtime_config.example.py   설정 작성 예시
  runtime_config.py           운영자가 실제 값을 입력하는 파일
  requirements.txt            설치할 Python 패키지
  backend/                    SSO·DB·등록·권한·API 코드
  frontend/                   화면 소스
  templates/                  HTML 템플릿
  static/                     화면 파일·폰트·배포 Skill ZIP
  receiver/                   다운로드 클라이언트 원본
  scripts/                    문서·Skill·화면 빌드 도구
  docs/                       운영 및 사용 문서
```

| 파일·위치 | 일반 운영자가 수정하나요? | 설명 |
|---|---|---|
| runtime_config.py | 예 | 실제 주소·사번·저장 경로 입력 |
| index.py | 보통 아니요 | 회사 기본 실행 코드와 포트 미지정 방식 유지 |
| web_main.py | 보통 아니요 | app = Flask(__name__) 생성 후 기존 플랫폼 기능 연결 |
| backend/auth.py | 보통 아니요 | 회사 SDK 인터페이스가 달라질 때 개발자가 검토 |
| 회사 실행기의 시작 설정 | 배포 담당자와 확인 | 작업 폴더·Python 확인, 기존 시작 방식·포트 유지 |
| templates·static | 설정 때문에 수정하지 않음 | 화면에서 주소·사번을 하드코딩하지 않음 |
| 직원 PC의 client.json | 명령으로 설정 | Skill이 사용할 웹 주소만 보관 |

기존 runtime_config.py가 있으면 먼저 백업하고 필요한 값만 수정합니다. 예시 파일로 덮어쓰면 기존 DB 주소와 저장 경로를 잃을 수 있습니다. 실제 설정 파일은 저장소에 커밋하거나 사용자에게 배포하지 않습니다.

## 4. 서버 Python과 패키지 준비

Windows 예시입니다. VS Code로 앱 폴더를 열고 **터미널 → 새 터미널**을 누릅니다. 아래 경로를 실제 배포 폴더로 바꿉니다. 회사가 Python 실행 환경을 제공하면 새 가상환경을 만드는 대신 그 실행 환경에 패키지를 설치합니다.

```powershell
Set-Location 'C:\apps\pt_ai_square'
python --version
python -m venv .venv
& '.\.venv\Scripts\python.exe' -m pip install -r requirements.txt
```

Python 3.11 이상을 사용합니다. .venv는 이 앱에 필요한 Python 패키지를 담는 별도 폴더입니다. 활성화 명령 없이 위 실행 파일을 직접 지정해도 됩니다. 설치에 쓴 Python과 회사 실행기가 쓰는 Python이 같아야 합니다.

SSO 운영에는 회사 hcputil도 필요합니다. 아래는 앞서 제공된 사내 저장소 설치 예시입니다. 회사 저장소 주소가 바뀌었다면 담당자가 안내한 주소를 사용합니다. 인터넷 공개 저장소에서 같은 이름의 패키지를 임의로 대체하지 않습니다.

```powershell
& '.\.venv\Scripts\python.exe' -m pip install hcputil --index-url http://nexus.skhynix.com:8080/repository/pypi-group/simple --trusted-host nexus.skhynix.com
& '.\.venv\Scripts\python.exe' -c "from flask import Flask; from pymongo import MongoClient; from hcputil.auth.sso import SSO; print('필수 모듈 확인 완료')"
```

마지막 명령의 성공은 모듈을 불러올 수 있다는 뜻입니다. 실제 SSO 로그인 성공까지 의미하지는 않습니다. 인터넷이 제한된 서버라면 회사 Python 패키지 저장소나 승인된 오프라인 패키지 설치 방식을 사용합니다.

## 5. runtime_config.py에 실제 값 입력하기

### 5-1. 파일 만들기

앱 폴더에서 runtime_config.example.py를 복사하여 같은 위치에 runtime_config.py라는 이름으로 저장합니다. 이미 파일이 있으면 새로 복사하지 말고 기존 파일을 엽니다. Windows에서 확장자가 숨겨져 있으면 runtime_config.py.txt가 되지 않았는지 확인합니다.

설정은 Python 문법입니다. 문자열은 따옴표로 감싸고, True·False는 아래처럼 대문자로 시작합니다. 줄 앞에 #이 붙으면 설명으로 처리되어 적용되지 않습니다. **.env 파일은 읽지 않습니다.**

### 5-2. SSO 운영 설정 예시

아래는 Windows 서버 예시입니다. MongoDB 주소·DB 이름·관리자 사번·저장 경로를 실제 값으로 바꾼 뒤 사용합니다. 예시 암호 문자열을 그대로 사용하면 연결되지 않습니다.

이 예시는 브라우저가 HTTPS로 접속하는 경우입니다. 현재 확인된 HTTP 접속 환경에는 아래 `PTAI_COOKIE_SECURE` 값만 `False`로 적용하며, 인증 방식은 `sso`를 유지합니다. SDK가 반환한 이동 주소의 scheme만 보고 쿠키 설정을 결정하지 않습니다.

```python
# 실제 자료를 저장하고 회사 로그인으로 사용합니다.
PTAI_DATA_MODE = 'mongodb'
PTAI_AUTH_MODE = 'sso'

# DB 담당자가 제공한 실제 연결 주소와 DB 이름으로 교체합니다.
MONGODB_URI = 'mongodb://DB_USER:DB_PASSWORD@DB_HOST:27017/?authSource=admin'
MONGODB_DATABASE = 'pt_ai_square'
PTAI_MONGODB_TIMEOUT_MS = 3000

# SSO에서 반환하는 실제 사번과 정확히 같게 입력합니다.
PTAI_ADMIN_IDS = '2069026,2069001'
PTAI_MOCK_ADMIN = False

# 브라우저는 회사 HTTPS 주소로 접속합니다.
PTAI_COOKIE_SECURE = True
PTAI_SESSION_COOKIE_NAME = 'pt_ai_square_session'

# 비워두면 MongoDB에 처음 생성한 세션 키를 보존해 재사용합니다.
PTAI_SECRET_KEY = ''

# 코드 재배포 후에도 남는 영구 저장 폴더를 지정합니다.
PTAI_DATA_DIR = r'D:\service-data\pt_ai_square'

# 초기 용량 정책: 요청 전체 128MB, 파일 저장 한도 50GB, 디스크 여유 10GB.
PTAI_MAX_UPLOAD_MB = 128
PTAI_STORAGE_QUOTA_MB = 51200
PTAI_STORAGE_RESERVE_MB = 10240

# 회사 기본 index.py의 실행 방식과 포트는 여기서 바꾸지 않습니다.
```

회사 기본 index.py는 `application.run(debug=True, host='0.0.0.0')`이며 별도 포트 인자가 없습니다. 0.0.0.0은 서버가 접속을 받는 범위이며 직원이 브라우저에 입력할 주소가 아닙니다. 직원에게는 회사에서 제공한 실제 서비스 주소를 안내합니다. `PTAI_HOST`·`PTAI_PORT`가 기존 설정에 있어도 index.py에는 적용되지 않습니다.

Linux·컨테이너에서는 PTAI_DATA_DIR을 실제 영구 볼륨 경로, 예를 들어 '/data/pt_ai_square'로 바꿉니다. 코드 폴더 안의 임시 디스크에 저장하면 재배포 때 파일이 사라질 수 있으므로 실제 마운트 유지 여부를 확인합니다.

### 5-3. 각 값이 바꾸는 것

| 설정 | 의미와 입력 방법 | 자주 헷갈리는 점 |
|---|---|---|
| PTAI_AUTH_MODE | sso: 실제 회사 사번, mock: 설정된 시험 사번 | SSO 주석 해제 대신 이 값을 바꿈 |
| PTAI_DATA_MODE | mongodb: 실제 저장, dummy: 가짜 목록 조회 | SSO 운영은 mongodb. dummy는 업로드 검증용이 아님 |
| MONGODB_URI | MongoDB 접속 경로·인증 정보 | 웹사이트 주소나 사용자 인증키를 넣는 곳이 아님 |
| MONGODB_DATABASE | 사용할 DB 이름 | 이름을 바꾸면 다른 DB를 사용하며 기존 자료가 자동 이동되지 않음 |
| PTAI_MONGODB_RETRY_WRITES | 선택 항목. 생략하면 False로 드라이버의 자동 쓰기 재시도 비활성화 | 기존 runtime_config.py에 추가할 필요 없음. 이 값이 URI의 retryWrites보다 우선하며 True는 해당 DB·실행 환경 검증 후 선택 |
| PTAI_ADMIN_IDS | 쉼표로 나눈 기본 관리자 사번 | 이름·이메일이 아닌 SSO 사번; 앞자리 0도 유지 |
| PTAI_COOKIE_SECURE | True이면 HTTPS에서만 앱 세션 쿠키 전송 | 실제 브라우저 접속이 HTTP이면 False, HTTPS이면 True; 프록시 내부 HTTP와 구분 |
| PTAI_SECRET_KEY | 세션 위조 방지용 앱 비밀키 | SSO 비밀번호나 API 인증키가 아님. 빈 값도 MongoDB 보존 방식으로 지원 |
| PTAI_DATA_DIR | 업로드 파일의 절대 경로 | DB 주소와 별개. 변경만 하면 기존 파일이 이동하지 않음 |
| PTAI_MAX_UPLOAD_MB | 한 HTTP 업로드 요청의 전체 크기 제한 | 파일 크기와 폼 정보가 함께 계산됨 |
| PTAI_STORAGE_QUOTA_MB | 관리자 설정 전 기본 파일 용량 한도 | 디스크 자체가 늘어나는 것은 아님 |
| PTAI_STORAGE_RESERVE_MB | 디스크에 남길 여유 공간 | 관리자 화면에서 한도 저장 후에는 DB의 정책이 우선 |
| PTAI_HOST·PTAI_PORT | 선택적인 로컬 보조 명령 __main__.py run에만 적용 | 회사 index.py·WSGI 실행 방식이나 포트를 바꾸지 않음 |
| PTAI_MOCK_USER·PTAI_MOCK_NAME | SSO 미사용일 때의 시험 신원 | SSO에서는 실제 로그인 신원을 사용하므로 운영 직원마다 설정하지 않음 |

MongoDB URI의 비밀번호에 @, :, / 같은 문자가 있으면 URI용 인코딩이 필요합니다. DB 담당자가 제공한 완성된 연결 문자열을 사용하는 것이 좋습니다. authSource는 계정을 인증할 DB이고 MONGODB_DATABASE는 앱 자료를 저장할 DB이므로 서로 다를 수 있습니다.

기존 설정 파일은 그대로 호환됩니다. `PTAI_MONGODB_RETRY_WRITES`가 없으면 새 기본값 `False`를 적용하므로 새 값을 입력하거나 URI를 수정할 필요가 없습니다. 이 옵션은 쓰기 결과 확인(write concern)이나 읽기 재시도(retryReads)를 바꾸지 않습니다. 자동 쓰기 재시도를 사용하려면 DB 종류·버전·구성과 회사 실행 환경을 검증한 뒤에만 `True`를 명시합니다. 225 오류와의 관계는 13-2절을 참고하세요.

직접 세션 키를 지정하고 싶다면 아래 명령으로 긴 무작위 값을 생성해 PTAI_SECRET_KEY에 입력합니다. 같은 서비스의 모든 작업 프로세스는 같은 값을 사용해야 합니다. 시작할 때마다 새로 생성하는 코드는 넣지 않습니다.

```powershell
& '.\.venv\Scripts\python.exe' -c "import secrets; print(secrets.token_hex(32))"
```

### 5-4. 파일을 고쳤는데 적용되지 않을 때

적용 우선순위는 **실행 프로세스의 환경변수 → runtime_config.py → 기본값**입니다. 회사 배포 설정에 PTAI_AUTH_MODE=mock이 남아 있으면 파일을 sso로 바꿔도 mock으로 동작합니다. MONGODB_URI와 MONGODB_DATABASE에는 PTAI_ 접두사를 붙이지 않습니다.

아래 명령은 현재 터미널에서 충돌 가능한 환경변수의 이름만 확인합니다. 비밀번호 값은 출력하지 않습니다. 회사 실행기가 별도 환경변수를 사용하는 경우 그 실행기 설정도 확인합니다.

```powershell
Get-ChildItem Env: | Where-Object { $_.Name -like 'PTAI_*' -or $_.Name -in @('MONGODB_URI','MONGODB_DATABASE') } | Select-Object -ExpandProperty Name
```

파일 저장만으로 실행 중인 서버가 바뀌지는 않습니다. 관련 서버 프로세스 또는 회사 배포 서비스를 재시작하고 브라우저를 새로고침합니다.

## 6. 회사 SSO 담당자와 맞춰야 할 부분

### 6-1. 앱에서 이미 준비된 부분

인증되지 않은 브라우저 접속은 /login?ORIGIN=원래주소로 이동합니다. 유효한 SSO 인증 세션이 없는 로그인 경로에서만 hcputil을 불러오고 SSO(request)를 만들어 요청 쿠키를 check_day_cookie()로 검사합니다. 성공하면 get_sso_info()로 아래 6개 정보를 받습니다. 일반 페이지 새로고침·API 조회·관리자 삭제 요청에서는 SDK를 다시 호출하지 않습니다.

| 순서 | 회사 예제의 이름 | 앱에서 쓰는 의미 |
|---|---|---|
| 1 | emp_no | 사용자 고유 사번. 등록자·승인·좋아요·다운로드와 연결 |
| 2 | emp_name | 화면 표시 이름 |
| 3 | emp_name_en | 영문 이름 세션 값 |
| 4 | dept | 소속 조직 이름 |
| 5 | email | 이메일 세션 값; 자동 메일 발송 설정을 뜻하지 않음 |
| 6 | dept_cd | 조직 코드. 조직 연결 시 사용 |

로그인한 사람의 정보는 앱 사용자 기록에 반영됩니다. 조직은 SSO 조직 코드, 그다음 조직명으로 찾아 연결하며, 없으면 새 조직 항목을 만듭니다. 사내 전체 인사 조직도를 자동 동기화하는 기능은 아닙니다. 운영 초기 여러 조직으로 로그인해 필터 분류가 의도대로 생성되는지 확인합니다.

회사에서 확인한 네 개의 세션 항목은 아래처럼 MongoDB에 연결됩니다. **기존 DB를 초기화하거나 사번 ID를 새로 만들 필요가 없습니다.** 인증된 SSO 로그인 때 기존 사용자 문서에 프로필 항목을 보완합니다.

| SSO 세션 | MongoDB users 문서 | 사용 예 |
|---|---|---|
| session['emp_no'] | 기존 _id 유지 + emp_no | 도구 등록자, 조회 승인, 연결 KEY의 동일한 사번 |
| session['emp_name'] | name·emp_name | 상단 표시 이름 |
| session['dept'] | dept | 현재 SSO 부서명 표시 |
| session['dept_cd'] | dept_cd, taxonomy의 ssoCode 연결 | 같은 부서 코드의 기존 조직 ID 연결 유지 |

예를 들어 사번 0012345의 이름이나 부서명이 바뀌어도 해당 사번이 등록한 도구와 받은 승인, 기존 KEY 연결은 유지됩니다. 사번 앞자리 0은 문자열로 보존합니다. 프로필은 인증된 SSO 로그인 때 갱신합니다. 세션에는 6개 프로필 값·logFlag와 함께 SSO로 인증한 신원·시각 표식을 저장하고 Flask가 서명합니다. logFlag나 프로필 문자열만 있는 이전 세션은 인증으로 인정하지 않으므로 업데이트 후 한 번 다시 로그인합니다.

앱 세션은 로그인 시점부터 **최대 8시간** 유효합니다. 새로고침이나 API 호출로 만료 시각을 연장하지 않습니다. 유효한 세션으로 /login에 다시 접속해도 SDK를 호출하지 않고 같은 서비스의 원래 주소로 돌아갑니다. 보호된 요청마다 MongoDB에서 현재 계정의 활성 상태와 관리자 역할·도구 권한을 확인하며, 웹의 변경 요청에는 기존 CSRF 검사를 적용합니다. API 인증키는 기존 키 인증 절차를 따릅니다. 세션이 없거나 만료되면 페이지는 로그인으로 이동하고 API는 로그인 주소를 포함한 401 JSON을 반환합니다. SSO 실패 시 mock 사용자로 자동 전환하지 않습니다.

**회사 SSO 로그아웃은 이미 발급한 앱 세션을 즉시 취소하지 않습니다.** 회사 쿠키가 만료되어도 앱 세션은 남은 시간 동안 유효할 수 있습니다. 플랫폼 로그아웃은 해당 앱 세션을 지우고, 로그인 후 8시간 만료 또는 MongoDB 계정 비활성화도 이후 접근을 차단합니다. 회사 SSO의 즉시 로그아웃 전파가 필요한 환경은 별도 연계가 필요합니다.

SSO에서 받은 현재 부서명(dept)과 관리자가 정한 검색·등록용 조직명(org)은 구분합니다. 상단 프로필은 현재 SSO 부서명을 표시하고, 관리자 화면에서 바꾼 조직 분류 이름은 기존 taxonomy 연결로 유지합니다. 따라서 관리자가 조직 이름을 편집했다고 해서 SSO 로그인 때 그 분류 이름을 강제로 원복하지 않습니다.

### 6-2. 회사 환경에서 확인할 사항

| 확인 사항 | 확인 요청 예시 | 정상 조건 |
|---|---|---|
| 서비스 등록 | “실제 서비스 주소에서 hcputil SSO를 쓰도록 등록되어 있나요?” | 회사 정책에 맞는 앱·주소 등록 완료 |
| 복귀 주소 | “ORIGIN과 /login 경로로 로그인 후 원래 서비스에 돌아올 수 있나요?” | 로그인 후 동일 서비스로 복귀 |
| 쿠키 전달 | “브라우저의 SSO Cookie가 프록시를 지나 Flask까지 전달되나요?” | SDK에서 쿠키 검증 가능 |
| 사용자 정보 | “get_sso_info가 사번·이름·영문명·부서·메일·부서코드 순으로 반환하나요?” | 현재 6개 값 계약과 일치 |
| 이동 주소 | “SDK redirect_url이 유효한 회사 로그인 이동 주소인가요?” | HTTP·HTTPS 절대 주소 또는 `/`로 시작하는 서비스 내 경로 반환 |
| 요청 주소 | “Flask가 보는 host와 scheme이 실제 브라우저 접속 주소와 일치하나요?” | ORIGIN 검사와 생성 링크가 실제 주소와 일치 |

SDK가 제공한 유효한 이동 주소의 호스트·scheme·포트는 보존합니다. HTTP 주소를 HTTPS로 강제 변경하지 않습니다. 위험한 scheme과 잘못된 URL 형식은 거절합니다. 요청자가 전달하는 ORIGIN은 별도 검사하며 계속 같은 서비스 주소만 허용합니다. SDK 이동 주소 지원을 넓힌다고 임의 외부 ORIGIN으로 이동할 수 있는 것은 아닙니다.

**현재 구현에는 프록시 헤더를 자동으로 신뢰하도록 하는 별도 설정이 없습니다.** 회사 실행기가 외부 scheme·호스트 정보를 올바르게 전달하면 그대로 사용합니다. 외부는 HTTPS인데 Flask가 내부 HTTP·내부 호스트로 인식한다면, 배포 담당자와 신뢰할 프록시 개수를 확인한 뒤 실행기 설정 또는 개발자의 프록시 처리 보완이 필요합니다. 확인 없이 ProxyFix를 추가하거나 임의의 X-Forwarded 헤더를 무조건 신뢰하도록 바꾸지 않습니다.

현재 기본은 https://서비스주소/처럼 루트 경로에 배포하는 방식입니다. https://서비스주소/ai-square/처럼 하위 경로에 올리는 것은 별도 경로 검증·개발이 필요할 수 있습니다. runtime_config.py에 임의의 URL_PREFIX를 넣는 것으로 해결되지 않습니다.

### 6-3. 굳이 수정하지 않아도 되는 코드

web_main.py에는 회사 예제처럼 `app = Flask(__name__)`, `NLS_LANG='.UTF8'`, `url_path=''`가 있습니다. 공용 초기화 함수가 이 앱에 `/`·`/login`과 기존 플랫폼 기능을 등록하므로 예제 함수를 추가로 붙이지 않습니다. hcputil import와 SDK 호출은 유효한 SSO 인증 세션이 없는 로그인 경로에서만 수행하여 로컬 mock에서는 hcputil 없이 실행할 수 있습니다. HTTPS 검증 경고를 전역으로 끄는 설정은 추가하지 않습니다.

### 6-4. 우측 상단 이름·부서·사진 확인

SSO로 로그인한 뒤 우측 상단에서 “이름 TL”, 부서명, 원형 사진을 확인합니다. TL은 요청한 화면 표기이며 SSO의 관리자 권한이나 직책 정보를 새로 만드는 값은 아닙니다.

사진 원본 주소는 http://skynet.skhynix.com/portalWeb/uploadfile/pictures/사번.jpg 형식입니다. 상단 프로필에는 HTTPS 플랫폼의 /api/me/photo 주소를 보여주고, 플랫폼 서버가 현재 로그인한 사번의 사진을 회사 주소에서 읽어 전달합니다. 구성원 순위에서는 /api/people/사번/photo 주소를 사용하며, 활성 계정이고 삭제되지 않은 도구를 등록한 구성원의 사진만 로그인한 사용자에게 제공합니다. 브라우저의 SSO 쿠키나 연결 KEY를 사진 서버로 전달하지 않습니다.

운영자는 **플랫폼 서버에서 회사 사진 서버에 접근할 수 있는지** 확인하면 됩니다. 사진이 없거나 연결되지 않으면 이름 첫 글자로 표시하며 나머지 기능은 계속 사용할 수 있습니다. mock·dummy 시험에서는 실제 사번 사진을 외부로 요청하지 않습니다. 실제 회사 사진 표시 여부는 사내 SSO 환경에서 확인합니다.

## 7. MongoDB와 파일 저장소 준비

### 7-1. MongoDB

서버에서 MongoDB 호스트로 접속할 수 있어야 합니다. 계정에는 지정 DB의 읽기·쓰기와 앱 시작 시 필요한 컬렉션·인덱스 생성 권한이 필요합니다. DB 담당자가 제공한 인증 방식·TLS 조건을 그대로 사용합니다. 앱 시작 시 연결을 확인하고 기본 자료와 인덱스를 준비합니다.

| 저장 대상 | MongoDB | 서버 파일 폴더 |
|---|---|---|
| 도구명·설명·관련 업무·등록자 | 저장 | 해당 없음 |
| 버전 번호·원본 파일명·크기·SHA-256·저장 경로 | 저장 | 실제 파일은 별도 저장 |
| EXE·ZIP·MD·PS1 등 배포 파일 원본 | 원본 바이너리는 저장하지 않음 | PTAI_DATA_DIR/artifacts |
| 기능 요청 설명·첨부 목록 | 저장 | 첨부 원본은 request_attachments |
| 권한 신청·승인·추가 관리자·알림 | 저장 | 해당 없음 |
| 좋아요·다운로드·개인 API 사용 이력 | 저장 | 해당 없음 |
| 인증키 | 원문 대신 해시·사번·권한·취소 상태 저장. 새 KEY는 기간 제한 없음, 기존 기간형 KEY의 만료일 유지 | 직원 배포 파일에 넣지 않음 |

현재 런타임은 MongoDB만 사용합니다. MongoDB 오류 시 SQLite나 가짜 데이터로 자동 전환하지 않습니다.

### 7-2. 파일 폴더

예를 들어 PTAI_DATA_DIR을 D:\service-data\pt_ai_square로 지정합니다. 서버 실행 계정이 이 폴더에서 파일 생성·읽기·삭제를 할 수 있어야 합니다. 폴더는 앱이 준비하지만 상위 위치에 대한 권한·영구 디스크 연결은 운영 환경에서 제공해야 합니다.

여러 서버 인스턴스를 사용한다면 같은 MongoDB뿐 아니라 같은 파일 저장소도 공유해야 합니다. 한 서버에만 파일이 있으면 다른 서버로 들어온 다운로드가 실패합니다. 현재 용량 검사의 프로세스 내 보호만으로 여러 서버의 동시 업로드 용량을 엄격히 통제할 수는 없으므로, 확장 배포 시 공유 저장소·운영 한도도 함께 검토합니다.

### 7-3. 파일 크기와 회사 프록시

앱의 기본 최대 업로드 요청은 128MB입니다. 회사 프록시가 10MB까지만 허용한다면 앱 설정을 늘려도 큰 파일은 올라가지 않습니다. 회사 실행기·프록시의 업로드 크기와 응답 시간 제한을 앱 정책에 맞춰 확인합니다. 기능 요청 첨부에는 별도로 파일당 20MB·최대 5개 제한이 있습니다.

## 8. 웹 서버 실행하기

### 회사 기본 index.py 구조 확인

`index.py`는 다음 형태를 그대로 사용합니다.

```python
from web_main import app as application

if __name__ == "__main__":
    application.run(debug=True, host='0.0.0.0')
```

직접 실행할 때는 위 `debug=True`도 그대로 적용됩니다. 회사 실행기가 모듈을 불러오기만 하면 `__name__`이 `__main__`이 아니므로 run()을 호출하지 않습니다. 이 경우 요청 처리는 회사 실행기가 담당합니다. 앱이 별도 포트나 Waitress 실행을 선택하지 않습니다.

### 방법 A. 회사 실행기가 Flask 앱을 불러오는 경우

회사 배포 화면에서 기존 설정을 확인합니다. 회사가 제공한 실행 방식을 이 문서만 보고 다른 방식으로 변경하지 않습니다.

| 항목 | 지정할 내용 |
|---|---|
| 작업 폴더 | index.py와 web_main.py가 있는 폴더 |
| Python | 패키지와 hcputil을 설치한 Python |
| 모듈·앱 진입점 | 회사 기본 index:application; 기존 web_main:app도 동일 앱으로 호환 |
| 내부 주소·포트 | 회사 기존 설정 유지 |
| 외부 주소 | 직원이 접속할 실제 회사 서비스 주소(HTTP 또는 HTTPS) |
| 영구 저장소 | PTAI_DATA_DIR에 연결된 폴더·볼륨 |

회사 실행기가 `index:application` 또는 `web_main:app`을 import하면 앱을 생성하고 기능만 연결합니다. 별도 `python index.py`를 동시에 실행하지 않습니다. 회사 실행기의 포트 설정을 따르며 `PTAI_HOST`·`PTAI_PORT`는 이 방식에 적용되지 않습니다.

### 방법 B. 직접 프로세스를 실행하는 경우

회사에서 기본 파일을 직접 실행하도록 안내한 경우 다음과 같이 index.py를 실행합니다. VS Code에서는 index.py를 열어 **Python 파일 실행**을 눌러도 됩니다. web_main.py는 앱 정의용이며 단독 실행으로 서버를 시작하지 않습니다.

```powershell
Set-Location 'C:\apps\pt_ai_square'
& '.\.venv\Scripts\python.exe' index.py
```

내부 서버는 회사 기본 Flask 실행 방식으로 시작하며, 직원은 회사에서 제공한 실제 서비스 주소로 접속합니다. 현재 확인된 주소는 HTTP이며, HTTPS를 제공하는 배포 환경에서는 브라우저가 HTTPS로 접속합니다. 이 명령 자체가 HTTPS 인증서를 발급하거나 회사 SSO를 등록해 주지는 않습니다. 수동 실행은 터미널이 종료되면 중단되므로 계속 운영할 때는 회사의 기존 프로세스 관리 방식을 사용합니다.

로컬에서 종전의 5080 보조 실행이 필요한 개발자는 `python __main__.py run`을 별도로 선택할 수 있습니다. `PTAI_HOST`·`PTAI_PORT`는 이 보조 명령에서만 사용하며 회사 기본 진입점을 대신하지 않습니다.

### 최초 상태 확인

회사 웹 주소 뒤에 /health를 붙여 접속합니다. 정상이라면 status가 ok이고 storage가 mongodb인 JSON이 나옵니다. 이는 해당 시점의 기본 DB 통신을 확인한 결과이며, 모든 컬렉션의 조회·쓰기, 계정 권한, 개별 쿼리의 성공을 보장하지 않습니다. /health는 인증 없이 상태를 확인하는 경로이므로 이 결과만으로 SSO 로그인이 확인된 것도 아닙니다.

그다음 실제 홈 주소로 접속합니다. SSO를 거쳐 돌아온 뒤 상단 사용자 이름·조직이 본인과 일치하는지 확인합니다. 기본 관리자 사번으로 로그인하면 관리자 탭이 보여야 합니다.

## 9. 첫 로그인 후 관리자 화면 설정

### 기본 관리자와 추가 관리자

1. PTAI_ADMIN_IDS에 넣은 본인 사번으로 회사 SSO 로그인합니다.
2. 상단 **관리자 → 관리자 설정**을 누릅니다.
3. 동료를 추가하려면 **관리자 추가**를 누릅니다.
4. 동료의 이름 또는 사번을 검색하고 **관리자 지정**을 누릅니다.
5. 동료는 새로고침한 뒤 관리자 탭을 확인합니다.

검색 대상자는 이 플랫폼에 한 번 로그인한 기록이 있어야 합니다. 검색되지 않으면 먼저 사이트에 접속하도록 안내합니다. 추가 관리자 지정·해제는 기본 관리자만 수행합니다. 기본 관리자를 바꾸려면 runtime_config.py의 PTAI_ADMIN_IDS를 수정하고 서버를 재시작합니다.

### 조직·업무 분류

**관리자 → 조직·업무 → 추가**를 누릅니다. 이름, 표시 순서, 사용 여부를 입력하고 **저장**합니다. 예를 들어 조직 “융합기술”, 업무 “장비 점검”을 등록합니다. 둘러보기의 필터와 도구 등록·수정 화면에 바로 반영되는지 확인합니다.

기존 항목은 연필 버튼으로 수정합니다. 사용 중지하면 새 등록 시 선택되지 않지만 기존 기록과 연결은 유지됩니다. SSO 로그인으로 조직이 자동 생성될 수도 있으므로 실제 조직명·코드를 확인한 뒤 정리합니다.

### 파일 저장 용량

**관리자 → 저장 공간**을 엽니다. **직접 지정**이면 플랫폼 최대 용량을 입력하고, **서버 여유 공간에 맞추기**이면 실제 남은 디스크 공간을 기준으로 계산합니다. 서버에 남겨둘 여유 공간도 입력하고 **한도 저장**을 누릅니다.

예: 최대 50GB, 여유 10GB. 저장 즉시 다음 업로드부터 적용됩니다. 사용량보다 작게 설정해도 기존 파일을 자동 삭제하지 않습니다. 이 화면에서 저장한 정책은 MongoDB에 보존되며 runtime_config.py의 초기 용량 값보다 우선합니다. 측정 대상은 파일 저장 폴더가 있는 디스크이며 원격 MongoDB 디스크는 아닙니다.

## 10. 실제 등록·권한·새 버전 확인 순서

운영 검수용 도구임을 이름에 표시하고 비밀자료가 없는 작은 파일로 확인합니다. 개발 환경의 가짜 목록이 아니라 mongodb 모드에서 수행해야 실제 동작이 확인됩니다.

1. 등록자가 **도구 등록**을 누르고 이름, 유형, 프로그램, 조직, 업무, 설명을 입력합니다.
2. 조회 설정을 **승인 후 조회**로 선택합니다. 목록은 다른 직원에게 보이지만 상세·파일은 승인 전까지 열리지 않습니다.
3. 파일·연결 단계에서 준비한 파일을 선택하고 설치·연결 안내를 입력합니다. 파일은 서버가 자동 EXE 변환하지 않습니다.
4. 확인·게시를 마친 뒤 **등록 관리**에서 본인의 도구와 현재 버전을 확인합니다.
5. 관리자도 등록자도 아닌 직원이 다른 브라우저 계정으로 접속해 도구를 누릅니다. 조회 권한 팝업에서 **조회 권한 신청**을 누릅니다.
6. 등록자는 **등록 관리 → 권한 관리 → 대기 → 승인**으로 처리합니다. 신청자는 알림과 상세 조회·다운로드 가능 여부를 확인합니다.
7. 등록자는 해당 도구의 **버전** 관리에서 새 파일을 게시하고 새 배포 번호를 확인합니다. 기존 도구 ID는 유지되어야 합니다.
8. 승인받은 직원이 다시 받거나 업데이트로 받았을 때 다운로드 총계가 늘지 않는지 확인합니다. 같은 사번·같은 도구는 웹·API를 합쳐 최초 1회만 집계합니다.

등록자와 관리자는 기본 조회·관리 권한이 있습니다. 승인받은 일반 사용자는 조회·다운로드가 가능하지만 도구 수정·삭제 권한까지 얻는 것은 아닙니다. 플랫폼에서 조회 승인을 받는 것과 MCP가 연결하는 회사 데이터의 접근 권한을 받는 것은 별개입니다.

### 10-1. 기여도 순위 확인

홈 순위 영역의 **기여도 순위**를 누릅니다. 이 화면은 도구를 공유한 구성원의 공유 기여도를 전체 기간 기준으로 보여줍니다. 본인이 다른 도구에서 누른 좋아요나 다운로드 횟수를 모으는 활동 순위가 아닙니다.

점수는 **등록한 도구 수 × 5 + 그 도구들이 받은 좋아요 수 × 2 + 고유 다운로드 수 × 1**입니다. 예를 들어 도구 2개를 등록했고 다른 동료에게 좋아요 7개와 고유 다운로드 3회를 받았다면 27점입니다.

같은 도구의 새 버전을 올려도 등록 도구 수는 늘지 않습니다. 본인 도구에 대한 본인의 좋아요·다운로드, 업데이트 수신, 같은 동료의 같은 도구 반복 수신은 점수를 추가하지 않습니다. 좋아요 취소와 삭제 도구는 제외하고 비활성 등록자는 순위에 표시하지 않습니다. 동점은 등록 수 → 받은 좋아요 수 → 고유 다운로드 수 → 사번 순으로 정렬합니다.

TOP 10은 기존 순위처럼 1~5위와 6~10위로 나누어 표시합니다. 정보 아이콘에서 산식을 확인하고 **집계 새로고침**으로 최신 값을 확인할 수 있습니다. 조회 승인이 필요한 도구도 등록자의 합계에는 포함되지만 이 화면에 해당 도구의 이름이나 내용을 공개하지 않습니다.

### 10-2. 카드 소개와 동작 흐름 확인

둘러보기 카드에는 태그와 별도로 도구 소개를 최대 두 줄로 표시합니다. 더 긴 설명은 도구 카드를 눌러 상세 소개에서 확인합니다.

배포 Skill로 준비한 도구라면 상세 소개에 **이렇게 동작해요.**가 나타날 수 있습니다. 예를 들어 “Excel 파일 받기 → 데이터 정리 → 점검 항목 비교 → 결과 보고서 만들기”처럼 순서대로 표시합니다.

이 그림은 배포 Skill이 실제 프로젝트를 확인하고 ai-square.json의 workflow.steps에 정리한 정보로 만듭니다. 웹이 자유로운 설명을 읽어 동작을 추측하거나 코드를 실행하는 기능은 아닙니다. 단계 정보는 선택 항목이며 없으면 흐름 그림을 표시하지 않습니다. 각 버전에 저장된 안내이므로 새 버전에서 처리 방식이 달라졌다면 등록자가 Skill에 흐름 정보도 갱신하도록 요청합니다.

## 11. 개인 API 인증키와 배포 Skill 연결

### 11-1. 직원이 인증키 만들기

1. 회사 HTTPS 웹 주소에서 SSO 로그인합니다.
2. 우측 상단 개인 프로필 옆의 **열쇠 아이콘**을 누르거나 주소 뒤에 /local-access를 붙입니다. 기존 **로컬에서 받기** 링크로도 같은 화면에 접속할 수 있습니다.
3. **내 연결 KEY**에서 KEY 이름을 입력합니다. 예: “내 업무 연결”. 이름은 구분용이며 사번 하나에 여러 활성 KEY가 생기는 것은 아닙니다.
4. 받기만 하면 **조회·다운로드**, 등록까지 하면 **업로드 포함**을 선택합니다. 유효기간 선택 항목은 없습니다.
5. 처음에는 **연결 KEY 발급 → KEY 복사**를 누르고 개인 프로그램의 숨김 입력란에 넣습니다.

새로 발급한 KEY는 유효기간 제한 없이 사용할 수 있습니다. **KEY 재발급**, **KEY 사용 취소**, 계정 비활성화 후에는 사용할 수 없습니다. 이전 버전에서 1일·7일·30일처럼 기간을 정해 발급한 KEY는 원래 만료일이 유지됩니다. 기간 제한 없이 사용하려면 재발급하며, 만료되거나 취소된 옛 KEY를 다시 활성화하지 않습니다.

**사번당 사용할 수 있는 연결 KEY는 하나입니다.** 분실했거나 교체할 때는 같은 화면의 **KEY 재발급**을 누릅니다. 새 KEY가 활성화되면 이전 KEY는 이후 API 인증에 사용할 수 없으므로, 기존에 연결한 프로그램에도 새 값을 입력해야 합니다. 이전 KEY로 호출하면 인증 실패가 표시되고 웹 세션이나 mock 신원으로 우회하지 않습니다.

예를 들어 다운로드 Skill에 KEY를 넣고 사용하던 직원이 KEY를 재발급했다면, 그 Skill의 다음 호출에도 새 KEY를 입력해야 합니다. CUBE 메신저·MCP·앱 연계를 추가할 때도 같은 사번 기반 연결 정보를 사용할 수 있도록 마련한 기능입니다. KEY 화면만으로 각 서비스의 실제 연동까지 완료되는 것은 아닙니다.

원문 KEY는 발급 직후 한 번만 표시하고 MongoDB에는 해시와 사번·권한·취소 정보를 저장합니다. `users._id`는 사번이고 `users.activeConnectionKeyId`는 현재 KEY ID입니다. `local_tokens.user`에 같은 사번을, `local_tokens._id`에 KEY의 SHA-256 해시를 저장하므로 발급한 KEY와 직원의 연결이 서버에 남습니다. 새 KEY의 `expires`는 `null`로 저장합니다. 재발급 시 사용자의 활성 KEY ID를 한 번에 교체하여 동시에 발급 요청이 들어와도 최종 활성 KEY만 인증됩니다. 이전 KEY 원문을 다시 조회하는 기능은 없습니다. 이전 기록은 사용 이력 집계를 위해 남지만 사용할 수는 없습니다.

이전 화면을 열어둔 채 발급하여 `days`가 포함된 옛 요청이 들어오면 서버는 400 응답으로 새로고침을 안내합니다. 화면을 새로고침한 다음 다시 발급합니다. KEY 데이터에 `expires` 필드가 없거나 잘못된 값이면 인증을 거절하고 재발급하도록 안내하며, 이를 기간 제한 없는 KEY로 해석하지 않습니다.

이전 버전에서 한 사번에 여러 KEY를 만들었다면, 새 구현의 첫 KEY 조회·인증 시 가장 최근의 유효한 KEY 하나를 현재 KEY로 연결합니다. 다른 이전 KEY는 인증되지 않습니다. 어떤 KEY인지 알 수 없다면 재발급 후 연결 프로그램의 값을 갱신합니다. 이 전환은 도구·버전·좋아요·다운로드 이력을 삭제하지 않습니다.

필요 없는 KEY는 같은 화면의 **KEY 사용 취소**로 폐기합니다. 회사 SSO에서 로그아웃해도 KEY가 자동 취소되지는 않습니다. 업로드 포함 KEY도 도구 삭제·관리자 설정·권한 승인에는 사용할 수 없습니다.

### 11-2. 직원 PC에 웹 주소 입력

다운로드만 필요하면 **다운로드용 Skill 받기**, 파일 준비와 게시까지 하려면 **배포·자동 등록 Skill 받기**를 누릅니다. ZIP을 풀고 SKILL.md가 있는 폴더에서 터미널을 엽니다.

```powershell
python scripts/square_client.py configure --url https://ai-square.example.com
python scripts/square_client.py auth
python scripts/square_client.py --authenticate search "회의록"
```

첫 줄의 주소를 실제 서비스 주소로 바꿉니다. auth는 인증키 발급 페이지를 브라우저에서 엽니다. --authenticate는 터미널에서 키를 화면에 표시하지 않고 입력받습니다. 키가 없으면 발급 페이지로 안내하지만 브라우저 쿠키에서 키를 자동 추출하지는 않습니다.

웹 주소는 사용자 홈 폴더의 .pt-ai-square/client.json에 baseUrl로 저장됩니다. 인증키나 DB 정보는 이 파일에 저장하지 않습니다. 원격 서버는 HTTPS여야 하며 localhost 시험만 HTTP를 허용합니다. 회사 인증서 검증 오류는 인증서 신뢰 설정을 담당자와 확인하여 해결합니다.

### 11-3. “플랫폼에 등록해줘” 흐름

배포·자동 등록 Skill에는 파일 준비 스크립트와 publish_client.py가 함께 있습니다. 다운로드만으로 사용 중인 모든 AI 프로그램에 자동 설치되지는 않습니다. 사용하는 AI의 Skill 등록 방식에 맞춰 추가하거나 해당 폴더의 SKILL.md를 읽도록 요청합니다.

예시 요청: “이 프로젝트를 배포 Skill로 준비하고 플랫폼에 등록해줘. 기존 도구라면 새 버전으로 올리고, 조직·업무·조회 공개 여부는 먼저 확인해줘.”

Skill은 파일·설명·유형 등을 준비하고 게시 계획을 만듭니다. 조직·업무·공개 여부를 추측해 게시하지 않고 확인합니다. 확인한 조직·업무 ID와 조회 설정으로 게시하며, 서버는 로그인한 사번에 연결된 키와 관리 권한을 검사합니다.

아래는 prepared.zip이 이미 있는 경우 개발자가 같은 작업을 직접 실행하는 예시입니다. 명령은 배포 Skill 폴더에서 실행합니다. 각 명령에서 인증키를 요청하면 업로드 포함 키를 숨김 입력란에 넣습니다.

```powershell
python scripts/publish_client.py prepare --artifact ./prepared.zip --plan ./publish-plan.json
python scripts/publish_client.py publish --plan ./publish-plan.json --visibility approval
```

prepare 결과에서 missing 항목과 조직·업무 선택지를 확인합니다. 필수 정보가 빠져 있으면 Skill을 통해 값을 보완한 뒤 게시합니다. approval은 승인 후 조회, public은 로그인한 사내 사용자에게 공개입니다. 계획 파일이 만들어졌다고 게시가 끝난 것은 아닙니다.

기존 도구는 로컬 관리 기록 또는 관리 가능한 동일 packageId를 기준으로 찾습니다. 여러 개라 모호하면 어떤 도구인지 확인합니다. 이름이 비슷하다는 이유만으로 덮어쓰지 않습니다. 게시 후 같은 도구 ID에 새 버전이 생겼는지 웹의 등록 관리에서 확인합니다.

응답을 못 받아 성공 여부가 불확실할 때는 **같은 계획 파일로 publish를 재시도**합니다. 서버가 같은 요청을 구분하여 중복 버전 생성을 방지합니다. 새 prepare를 먼저 실행하면 새 요청이 될 수 있습니다.

### 11-4. 버전 확인·다운로드 집계

```powershell
python scripts/square_client.py --authenticate check 12 --release 1
python scripts/square_client.py --authenticate download 12 --output ./downloads
python scripts/square_client.py --authenticate download 12 --output ./updates --update
```

12는 실제 검색 결과의 도구 ID, 1은 사용 중인 배포 번호로 바꿉니다. check는 최신 여부를 확인하고 PC의 설치 파일을 바꾸지 않습니다. download는 파일을 받아 크기와 SHA-256을 비교하지만 자동 설치·실행하지 않습니다. --update 수신은 다운로드 집계에서 제외합니다. 일반 수신도 동일 사번·도구는 최초 1회만 집계하며 반복 전송 이력은 남습니다.

도구 실행 때마다 버전을 확인하려면 해당 도구의 실행 진입점에서 제공된 버전 확인 기능을 호출하도록 연결해야 합니다. 플랫폼에 파일을 올리는 것만으로 이미 설치된 모든 프로그램에 자동 확인 기능이 생기지는 않습니다.

| 관리자 탭 없음 | 실제 SSO 사번과 ADMIN_IDS | 사번 문자열 일치, 환경변수 충돌, 재시작 여부 확인 |

| 브라우저 API 401 | 앱 세션 없음·8시간 만료·이전 세션의 인증 표식 누락 | 응답의 로그인 주소로 이동해 다시 로그인 |
| API 인증키 401 | 키 누락·만료·취소·재발급으로 교체됨 | /local-access에서 현재 KEY 확인 또는 재발급 후 연결 프로그램 값도 갱신 |
| API 업로드 403 | 조회 전용 키·타인 도구 | 업로드 포함 키와 해당 도구 관리 권한 확인 |
| 게시 409 | 변경된 버전·재사용 계획과 내용 불일치 | 현재 도구를 다시 확인하고 새로운 계획 작성; 단순 응답 유실은 같은 계획 재시도 |
| 인증서 오류 | 사내 인증서 체인·PC 신뢰 설정 | 담당자에게 올바른 신뢰 체인 구성 요청 |

SSO SDK 실패 로그는 `HCP SSO failure stage=... error=...` 형식으로 실패 단계와 예외 유형만 남깁니다. 쿠키·인증키·사번·예외 메시지 원문은 남기지 않습니다. MongoDB 예외는 전역 DB 오류 처리에서 별도 503으로 반환하며 HCP SSO 실패로 표시하지 않습니다.

SDK 이동 주소 검증 실패는 `HCP SSO failure stage=redirect_url reason=<code>`의 사유 코드로 확인합니다. 예를 들어 `unsupported_scheme`은 허용하지 않는 scheme, `malformed_url`은 잘못된 URL 형식입니다. 전체 이동 URL·쿼리·쿠키는 로그에 남기지 않습니다. 기존 코드가 HTTP 주소나 서비스 내 경로를 거절한 오류는 이동 주소 검증 문제이며, `PTAI_AUTH_MODE = 'sso'` 설정 오류가 아닙니다. 인증 방식을 mock으로 바꾸지 않습니다.

장애 문의에는 발생 시각, 접속 URL, 화면 오류, 어떤 계정 역할로 어떤 버튼을 눌렀는지를 남깁니다. 인증키 원문, 쿠키, 비밀번호 포함 MongoDB URI는 로그나 공유 문서에 붙이지 않습니다.

### 13-1. 서버 로그를 볼 수 없을 때 MongoDB 오류 확인

`/health`가 `status=ok`, `storage=mongodb`여도 특정 화면에서 오류가 날 수 있습니다. 기본 통신과 개별 조회·쓰기·권한 검사는 서로 다릅니다. 현재 운영에서 발생한 오류의 실제 원인은 아직 확인되지 않았으며, 아래 진단값으로 범위를 좁혀야 합니다.

조회나 주 저장 작업의 MongoDB 오류는 HTTP 503으로 반환됩니다. 페이지 이동 중에는 별도 오류 안내 화면이 열리고, 화면 안의 API 요청은 해당 오류 표시 위치 한 곳에 안내가 나옵니다. 저장이 끝난 뒤 이력·알림 등 후속 처리만 남으면 13-2절의 `pending` 안내로 구분합니다. **진단 코드**, 제공된 경우 **MongoDB 숫자 코드**, **12자리 문의 번호**(숫자와 a~f로 구성)를 확인하세요. 문의 번호는 한 번의 오류 응답을 구분하는 값입니다. 화면이나 API 응답에는 접속 URI·비밀번호·쿠키·세션 신원·원본 예외 내용을 포함하지 않습니다.

1. `config.py`를 포함한 새 앱 코드를 반영하고 기존 회사 실행기 또는 `index.py`를 같은 명령·포트로 재시작합니다. 실제 설정인 `runtime_config.py`, 업로드 폴더와 MongoDB 자료는 보존합니다. 필수로 추가할 설정은 없습니다.
2. 오류가 난 동작을 한 번 확인합니다. 조회는 같은 화면·버튼으로 다시 실행합니다. 등록·저장·삭제는 목록이나 상세 화면에서 **이미 반영됐는지 먼저 확인**하고, 미반영이 확인된 경우에만 한 번 다시 실행합니다. 반영 여부가 불분명하면 반복 실행하지 말고 담당자에게 확인합니다. 앱은 실패한 변경 요청 전체를 자동 재실행하지 않습니다. 저장 완료 후 남은 이력·알림 등 후속 처리의 재시도는 아래 13-2절과 같이 구분합니다.
3. 다시 오류가 나면 발생 시각, 화면·버튼 또는 실행한 API 동작, 진단 코드, MongoDB 숫자 코드(표시된 경우), 문의 번호를 기록합니다. 예: `관리자에서 검수용 항목 삭제 / DB-PERMISSION / MongoDB 13 / 문의 012345abcdef`는 기록 형식의 예시입니다.
4. 아래 표에 따라 개발·DB 담당자에게 이 기록을 전달합니다. 진단값 없이 설정을 바꾸거나 DB를 초기화하지 않습니다. 인증 방식을 mock으로 바꾸지 않습니다.

| 진단 코드 | 의미 | 담당자와 확인할 다음 항목 |
|---|---|---|
| `DB-CONNECTION` | 연결 불가 또는 통신 중단 | 앱 서버에서 DB로 가는 네트워크·TLS·DB 가동 상태 |
| `DB-TIMEOUT` | 조회·쓰기 응답 시간 초과 | 해당 동작의 쿼리·DB 부하; 쓰기는 실제 반영 여부부터 확인 |
| `DB-SESSION-ORDER` | 같은 DB 세션의 요청 번호 순서 충돌, MongoDB 225 | 새 코드 적용과 모든 기존 작업 프로세스 재시작 여부; 계속되면 발생 동작·숫자 코드·문의 번호 전달 |
| `DB-AUTHENTICATION` | DB 계정 인증 실패, MongoDB 18 | 서버에 적용된 계정·인증 DB(authSource)·인증 설정 |
| `DB-PERMISSION` | 해당 DB 작업 권한 부족, MongoDB 13 | 대상 DB·컬렉션에서 필요한 읽기·쓰기·인덱스 작업 권한 |
| `DB-DUPLICATE` | 고유 값 중복, MongoDB 11000 | 기존 저장 결과와 중복을 막는 인덱스; 기존 자료를 임의 삭제하지 않음 |
| `DB-DOCUMENT` | 컬렉션 문서 검증 실패, MongoDB 121 | 저장하려던 항목과 DB의 필수 필드·자료형 등 입력 규칙 |
| `DB-BULK-WRITE` | 여러 문서의 일괄 쓰기 실패 | 일부 반영 여부, 표시된 숫자 코드와 실패한 동작 |
| `DB-OPERATION` | 그 밖의 MongoDB 작업 실패 | **표시된 MongoDB 숫자 코드**와 실행 동작을 함께 전달하여 원인 확인 |
| `DB-ERROR` | 그 밖의 MongoDB 처리 오류 | 문의 번호·발생 시각·실행 동작으로 개발 담당자가 추가 확인 |

진단 코드는 원인을 좁히는 분류이며, 문서나 로컬 시험만으로 운영 장애가 해결됐다고 판단하지 않습니다. 필요한 조치 후 실제 오류가 났던 동작과 저장 결과를 다시 확인합니다.

### 13-2. 게시·좋아요·한도 저장에서 MongoDB 225가 보일 때

**225(`TransactionTooOld`)는 같은 DB 세션에서 이미 처리 중이거나 처리된 번호보다 이전 번호의 요청이 도착했다는 뜻입니다.** 예를 들어 DB가 20번 요청을 받은 뒤 같은 세션의 19번 요청을 받으면 거절할 수 있습니다. 여기서 세션은 앱과 DB 사이의 요청 관리 단위이며, “오래된 파일이나 DB 자료를 지우라”는 뜻이 아닙니다. 코드 이름은 [MongoDB 공식 오류 코드](https://www.mongodb.com/docs/manual/reference/error-codes/)에서, 번호 순서의 의미는 [MongoDB의 TransactionTooOld 설명](https://github.com/mongodb/mongo/blob/master/src/mongo/db/repl/README.md#transactiontooold-errors)에서 확인할 수 있습니다.

앱에서 여러 문서를 묶는 트랜잭션을 직접 시작하지 않아도 드라이버의 자동 쓰기 재시도 과정에서 요청 번호가 사용될 수 있습니다. 새 코드는 기본적으로 `retryWrites=False`를 명시해 이 경로를 사용하지 않습니다. DB에 쓰기 결과를 확인받는 동작과 읽기 재시도 설정은 유지됩니다. 자동 쓰기 재시도의 지원 조건과 동작은 [MongoDB 공식 Retryable Writes 문서](https://www.mongodb.com/docs/manual/core/retryable-writes/)를 참고하세요. 이 옵션이 모든 225 오류나 다른 DB 오류를 해결한다는 뜻은 아닙니다.

현재 회사 환경에서 번호 순서가 어긋난 정확한 원인은 확정되지 않았습니다. 프로세스 복제 때 DB 연결이 함께 상속되는 경우, 세션 재사용, DB 제품·드라이버의 호환성을 확인할 필요가 있습니다. 새 코드는 프로세스 ID를 확인하여 각 작업 프로세스가 자기 `MongoClient`와 연결 풀을 사용하게 합니다. 같은 프로세스의 여러 스레드는 하나의 클라이언트를 공유합니다. 로컬 임시 DB에서 번호 순서를 어긋나게 한 재현과 후속 처리 실패 시험은 코드 동작을 확인하는 범위이며, 회사 운영 환경의 원인 확인을 대신하지 않습니다.

이번 수정에서 저장 결과와 안내는 다음처럼 구분됩니다.

| 화면 상황 | 처리와 확인 방법 |
|---|---|
| 게시·한도·도구 관리·권한 등의 저장은 완료했지만 이력·구독·알림 후속 처리 실패 | 주 기록과 같은 문서에 남긴 outbox를 관련 저장 요청 또는 알림 조회에서 처리합니다. pending 등 대기 상태와 이미 저장된 결과를 구분하며 같은 작업 ID로 중복을 방지합니다. 홈 목록 조회 자체는 이 후속 작업을 실행하지 않습니다. |
| 좋아요 저장은 완료했지만 활동 이력 반영 지연 | 좋아요 상태와 함께 보관한 대기 이력을 해당 도구·사용자 범위 또는 알림 조회에서 다시 처리합니다. historyPending으로 구분하며 같은 도구의 요청이 진행 중이면 다른 카드에서도 연타를 막습니다. |
| 좋아요는 저장됐지만 현재 총 개수 조회 실패 | count=null, countsPending으로 저장 성공과 집계 지연을 구분합니다. 화면은 이전 숫자에 저장된 선택의 변화만 반영해 임시 표시하고 다음 정상 목록 조회에서 서버 집계로 바꿉니다. |
| 게시·수정·승인 등 변경 완료 응답 후 목록·상세 조회만 실패 | 변경이 저장됐다는 사실과 조회 실패를 구분해 안내합니다. 새로고침으로 실제 저장 결과를 확인하고, 저장 버튼부터 반복해서 누르지 않습니다. |
| 한도 저장 성공 | 응답의 저장 한도·revision을 바로 반영하며 전체 목록을 다시 읽지 않습니다. 저장 전에 시작한 오래된 목록 응답이 새 한도를 덮어쓰지 않습니다. |
| 쓰기 자체가 실패하거나 결과를 확인할 수 없음 | 해당 화면 한 곳에 오류를 표시합니다. 진단 코드·문의 번호를 기록하고 실제 반영 여부부터 확인합니다. |

웹 게시 화면은 같은 내용·파일·게시 대상의 재시도에 요청 ID를 유지하여 중복 등록·버전을 방지하고, 게시 중 다른 호출이 들어와도 동시에 두 번 전송하지 않습니다. 페이지를 닫거나 새로고침한 뒤까지 이 ID를 영구 보관하는 기능은 아닙니다. 내용을 바꾸거나 화면을 새로 열었다면 등록 관리에서 결과를 먼저 확인합니다. API 배포 Skill은 11-3절의 같은 계획 파일로 재시도합니다. 서로 다른 화면에서 목록을 요청해도 먼저 시작한 오래된 응답·오류가 최신 응답을 덮어쓰지 않도록 처리합니다.

outbox는 **“저장은 끝났고, 기록·알림 전달만 남았다”는 작업 목록**입니다. 예를 들어 새 버전 게시와 알림 작업을 같은 도구 문서에 저장합니다. 알림 전달 중 오류가 나도 새 버전은 유지되고, 전달을 마친 작업만 목록에서 지웁니다. 같은 이벤트를 다시 전달해도 이력·알림이 중복되지 않으며, 사용자가 알림을 꺼 둔 구독을 지연된 자동 구독으로 다시 켜지 않습니다. 여러 문서를 하나의 트랜잭션으로 묶는 방식이 아니라, 한 문서의 변경을 한 번에 저장하는 MongoDB 동작을 사용합니다.

대상은 `tools`, `access`, `feedback`, `ideas`, `administrators`, `settings`, `taxonomy`, `users`이며 이전 버전의 `postCommit` 작업도 호환 처리합니다. 일반 전달은 컬렉션당 최대 50개 문서·문서당 최대 50개 이벤트, 활동 이력은 한 번에 최대 50개 상태 문서를 처리합니다. 한 이벤트의 실패가 다른 이벤트 처리를 모두 막지 않게 분리하지만, 이 숫자가 전체 응답 시간의 상한을 보장하지는 않습니다.

남은 후속 작업은 **알림 조회**가 다시 처리합니다. 브라우저가 열려 있고 요청이 정상 수행되면 기존 약 30초 확인 주기를 이용합니다. 별도의 상주 백그라운드 worker를 추가한 것은 아니므로 접속자가 없거나 DB 오류가 계속되면 작업이 남아 있습니다. `/api/bootstrap`에는 전체 대기 이력·알림 쓰기가 없어, 다른 사람의 대기 작업 때문에 현재 홈 목록 조회가 실패하던 경로를 제거했습니다. 다만 목록 자체의 DB 조회가 실패하면 오류가 날 수 있습니다.

연결 KEY는 활성 KEY 포인터 변경과 이력을 같은 사용자 문서에 저장합니다. 이전 KEY의 취소·교체 표시가 지연돼도 인증에는 현재 포인터 일치 여부를 사용하며, KEY 원문을 outbox에 남기지 않습니다. 다운로드는 원본 상태 저장 성공 후 이력·자동 구독 전달이 실패해도 파일 응답을 막지 않습니다. 원본 상태 저장 자체가 실패한 경우까지 성공 처리하지는 않습니다.

기능 요청 첨부는 등록 오류가 나면 DB 참조를 확인하여 **미참조가 확인된 파일만** 정리합니다. 이미 참조된 파일이나 DB 조회 실패로 참조 여부를 확인하지 못한 파일은 보존합니다. 보존된 미참조 파일을 주기적으로 자동 삭제하는 작업은 없으므로 장애 후 운영 점검이 필요합니다.

운영 반영은 다음 순서로 진행합니다.

1. `runtime_config.py`, 업로드 폴더, 기존 MongoDB를 보존하고 `config.py`를 포함한 새 코드를 배포합니다. 기존 설정 파일에 필수로 추가할 값은 없습니다.
2. 회사의 기존 배포·재시작 절차로 **모든 기존 작업 프로세스**를 교체합니다. 여러 작업 프로세스 중 일부에 이전 코드와 DB 연결이 남지 않도록 확인합니다. `index.py` 실행 방식·시작 명령·포트는 유지합니다.
3. 로그인 후 검수용 게시 1회, 좋아요 1회, 저장 공간 한도 저장 1회를 각각 실행합니다. 한도는 승인된 운영 값을 사용합니다. 각 결과를 새로고침한 뒤에도 게시 버전·좋아요·설정 값이 유지되는지 확인합니다.
4. 브라우저에서 이전 화면 코드가 보이면 Ctrl+F5로 새로고침합니다. 225가 계속 보이면 발생 시각, 실행 동작, `DB-SESSION-ORDER`, MongoDB 숫자 코드, 문의 번호를 개발·DB 담당자에게 전달합니다. 로그의 HTTP method·route 템플릿·retry_writes를 함께 확인합니다. DB 주소·암호·쿠키·인증키 원문은 필요하지 않습니다.

### 13-3. 데이터를 바꾸지 않고 연결 상태 확인하기

앱 서버에서 실행 프로그램과 **같은 Python**을 사용합니다. 먼저 터미널에서 `web_main.py`가 들어 있는 `pt_ai_square` 폴더로 이동한 뒤 다음 명령을 실행합니다. Python 실행 파일의 전체 경로로 앱을 실행했다면 여기서도 같은 실행 파일을 사용합니다.

```powershell
python scripts/diagnose_mongo.py
```

진단은 웹과 같은 `mongo_client(config)` 연결 옵션 생성 함수를 이용합니다. `ping`, `hello`, `buildInfo`만 요청하고, DB·문서 생성·인덱스 변경·데이터 쓰기는 하지 않습니다. 접속 주소·계정·비밀번호·세션 ID·원문 서버 오류는 출력하지 않습니다. 성공한 진단 항목으로 현재 통신·세션·복제 세트 정보를 확인하되, 정보 조회가 허용되지 않은 항목은 추가 확인이 필요합니다.

**ping이 성공해도 도구 등록 권한이나 모든 쓰기가 성공한다는 뜻은 아닙니다.** 진단은 별도 Python 프로세스이므로 웹 프로세스를 재시작하지 않았다면 서로 다른 설정을 사용하고 있을 수 있습니다. 코드와 설정 반영 뒤 기존 회사 절차로 모든 웹 작업 프로세스를 교체하고, 실제 화면의 등록·좋아요·한도 저장 결과도 확인해야 합니다.

2026-10-23에 사용자가 전달한 운영 진단과 확인은 아래와 같습니다.

| 항목 | 사용자 제공 결과 | 해석 범위 |
|---|---|---|
| retryWrites / ping | false / ok | 해당 진단 프로세스의 옵션과 그 시점의 기본 통신 |
| maxWireVersion / sessionsSupported | 13 / true | 서버가 응답한 프로토콜·세션 지원 정보 |
| replicaSet / router | true / false | 진단 응답상 복제 세트이며 mongos 라우터가 아님 |
| version | 5.0.11-10 | 서버가 전달한 버전 문자열; 이것만으로 DB 제품을 확정하지 않음 |
| 운영 수정 후 확인 | 정상 실행됐다는 사용자 확인 | 모든 기능·동시성·장기 운영의 전수 검증은 아님 |

이 결과는 사용자 제공 운영 관찰입니다. 이 저장소의 개발 환경에서 회사 DB에 직접 접속해 독립적으로 재확인한 결과가 아니며, 225의 서버 측 발생 원인을 확정하지 않습니다. 로컬 임시 DB·오류 주입·화면 테스트는 코드의 실패 경계를 검증하는 별도 증거입니다. 사용자 보고서의 Percona 추정도 제품 확정으로 보지 않으며 제품은 DB 운영자에게 확인해야 합니다.

현재 코드의 진단 이름은 호환성을 위해 `DB-SESSION-ORDER`를 유지합니다. 운영 보고서의 `DB-TRANSACTION-ORDER`와 같은 MongoDB 숫자 코드 225를 가리킵니다. 문의 번호로 서버 로그를 찾고 HTTP method·route 템플릿·retry_writes를 확인합니다. 후속 작업 지연은 `MongoDB follow-up deferred` 로그와 원본 문서의 outbox 또는 이전 postCommit 대기 항목으로 구분하며, 접속 정보나 인증키 원문을 로그·문의 자료에 추가하지 않습니다.

## 14. 업데이트·백업·설정 변경 시 지킬 순서

### 앱 코드 업데이트

1. 현재 코드 버전, runtime_config.py, MongoDB, PTAI_DATA_DIR을 보존합니다.
2. 쓰기 작업을 중단하는 점검 시간에 서버를 멈추거나 회사 배포 절차를 진행합니다.
3. 새 코드를 배포하되 운영 설정·영구 파일 저장소를 덮어쓰지 않습니다.
4. 필요한 패키지를 같은 Python 환경에 반영하고 회사의 기존 절차로 모든 작업 프로세스를 재시작합니다. 직접 실행은 index.py, 앱 불러오기는 index:application 또는 기존 web_main:app입니다. 별도 포트 변경은 하지 않습니다.
5. /health → SSO 한 번 로그인 → 홈 새로고침·일반 API 조회 → 관리자 검수용 항목 삭제 → 기존 파일 다운로드 순서로 확인합니다. 삭제 검수에는 미리 만든 시험 항목을 사용합니다.

새로고침·관리자 삭제의 반복 SSO 호출 수정에는 새 환경설정이 필요하지 않습니다. `runtime_config.py`, 업로드 폴더, 기존 MongoDB를 그대로 사용합니다. 배포 전 세션에는 새 SSO 인증 표식이 없으므로 한 번 재로그인해야 하며, 이후 8시간의 세션 유효기간 동안 SDK를 일반 요청에서 반복 호출하지 않습니다.

SDK 이동 주소 검증 수정도 새 설정 항목을 추가하지 않습니다. **수정 코드 반영 → 기존 설정 보존(`AUTH_MODE='sso'` 유지, 현재 실제 HTTP 접속은 `COOKIE_SECURE=False`) → 기존 프로세스를 같은 명령·포트로 재시작 → 회사 주소에서 로그인·새로고침 확인** 순서로 적용합니다. 운영 `runtime_config.py`를 예시 파일로 덮어쓰지 않습니다. 실제 회사 SDK와 SSO 서버를 통한 로그인 성공은 이 확인 후 판단합니다.

MongoDB 쓰기 안정화는 `config.py`를 포함한 새 코드로 적용합니다. 실제 `runtime_config.py`, 업로드 폴더와 기존 MongoDB는 보존하며 필수로 추가할 설정은 없습니다. 선택 항목 `PTAI_MONGODB_RETRY_WRITES`가 없으면 `False`를 적용합니다. 모든 작업 프로세스를 같은 실행 방식·포트로 재시작한 뒤 13-2절의 게시·좋아요·한도 저장과 새로고침을 확인합니다. 225가 남으면 13-1절의 진단값과 실행 동작을 함께 전달합니다.

DB와 파일은 연결되어 있으므로 같은 시점 기준으로 백업합니다. 코드만 되돌리는 것으로 DB 구조 변경까지 복구되는 것은 아닙니다. DB나 저장 경로를 바꿀 때는 자료 이전·복구 계획을 함께 준비합니다.

### 등록된 도구의 버전 되돌리기

앱 코드 배포와 도구 파일 배포는 다른 작업입니다. 도구 파일에 문제가 있으면 등록자·관리자가 버전 관리 화면에서 보존된 이전 버전으로 배포를 되돌립니다. 이미 PC에 받은 파일을 웹이 강제로 지우거나 교체하지는 않습니다. 버전 확인 시 현재 활성 배포를 기준으로 안내하게 됩니다.

이전 파일 정리는 **관리자 → 저장 공간 → 이전 버전 정리**에서 대상을 확인하고 진행합니다. 보존 정책과 정리 결과를 확인하고 필요한 복구 버전을 먼저 확보합니다. 파일을 실제 삭제한 버전은 번호·기록이 남아 있어도 원본 파일 복구 없이는 다시 배포할 수 없습니다. 용량 자동 계산이 오래된 파일을 자동 삭제하는 기능은 아닙니다.

### 로컬 SSO 미사용 시험으로 돌아가기

운영 서버를 mock으로 바꾸기보다 별도 PC·시험 DB·시험 파일 폴더에서 확인합니다. mock에서도 실제 데이터 쓰기가 일어나므로 운영 DB를 연결한 채 시험 사번으로 등록하면 운영 자료가 변경됩니다.

```python
PTAI_AUTH_MODE = 'mock'
PTAI_DATA_MODE = 'mongodb'
PTAI_MOCK_USER = '1000001'
PTAI_MOCK_NAME = '시험 사용자'
PTAI_MOCK_ADMIN = True
PTAI_COOKIE_SECURE = False
# MONGODB_URI / MONGODB_DATABASE / PTAI_DATA_DIR도 시험용으로 지정합니다.
```

mock은 외부 직원용 인증 방식이 아닙니다. 운영 복귀 시 sso로 되돌리고 회사의 실제 서비스 주소에서 로그인합니다. 쿠키 설정은 실제 접속이 HTTP이면 False, HTTPS이면 True로 맞춥니다.

## 15. 운영 인수인계 기록 양식

비밀번호와 키 원문을 제외한 아래 정보를 운영 문서에 기록합니다.

| 항목 | 실제 운영 값·결과 |
|---|---|
| 실제 서비스 주소와 HTTP·HTTPS 구분 | 입력 |
| 배포 책임자·SSO 담당자·DB 담당자 | 입력 |
| 서버 앱 폴더·Python 경로 | 입력 |
| 회사 실행기 및 진입점 | 입력 / web_main:app |
| MongoDB DB 이름·보안 설정 보관 위치 | 입력; URI 암호는 적지 않음 |
| 영구 파일 저장 경로 | 입력 |
| 기본 관리자 사번 | 입력 |
| 업로드·용량·보존 정책 | 입력 |
| DB+파일 백업 위치·주기·복구 담당자 | 입력 |
| SSO·등록·권한·API·버전 검수 일시 | 입력 |
| 마지막 배포 버전·되돌릴 코드 위치 | 입력 |

이 문서는 운영 담당자용 별도 문서입니다. 웹의 가이드 다운로드는 사용자·등록자용으로 유지하며, 실제 접속 정보가 들어간 운영 설정을 일반 사용자에게 배포하지 않습니다.
