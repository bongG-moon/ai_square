# P&T AI SQUARE 실행·운영 가이드

웹 서버를 실행하는 담당자용입니다. 웹에서 내려받는 사용자·등록자 가이드와 분리되어 있습니다.

## 개인 일괄·부서 조회 권한

등록자와 관리자는 기능의 **권한** 버튼에서 사번을 최대 100명씩 추가하거나 **팀·부서로 추가**에서 부서 권한을 설정합니다. 사번 확인과 기존 부서 검색은 사이트에 로그인한 적이 있는 활성 사용자 정보를 사용하며 회사 전체 부서 목록을 조회하지 않습니다. **부서 코드 직접 입력** 또는 **부서명 직접 입력**은 구성원의 로그인 이력이 없어도 규칙을 미리 저장할 수 있습니다. 권한을 설정하는 등록자·관리자 본인의 로그인은 여전히 필요합니다. 목록·신청 노출 범위와 실제 상세 조회·다운로드 검사는 기존과 같이 서버가 결정하며, 관리자 KEY를 포함한 API KEY는 이 권한 관리 API를 호출할 수 없습니다.

기존 개인 권한은 MongoDB `access` 문서를 유지합니다. 부서 규칙은 해당 `tools` 문서의 `departmentGrants` 배열에 저장하며, 버전별 설치 파일이나 검색용 조직 분류와 분리됩니다. 코드 규칙은 `users.dept_cd`가 같은 활성 사용자에게 적용합니다. 직접 입력으로 명시한 이름 규칙은 `users.dept`가 정확히 같은 활성 사용자에게 부서 코드 유무와 관계없이 적용합니다. 기존 검색에서 추가한 코드 없는 이름 규칙은 코드도 없는 사용자에게만 적용하는 의미를 유지합니다. 입력 문구로 코드·이름을 추정하거나 기존 규칙의 적용 범위를 자동 확대하지 않습니다.

직접 입력은 쉼표로만 구분하고 값마다 앞뒤 공백을 제거합니다. 내부 공백은 보존하며 빈 항목과 중복은 추가하지 않습니다. 한 도구의 부서 규칙은 최대 50개입니다. 부서 코드 등록을 권장하며, 코드 규칙을 미리 저장한 뒤 해당 코드의 구성원이 정상 SSO 로그인하면 권한이 적용됩니다. 소속은 DB에 저장된 마지막 정상 SSO 로그인 정보가 기준이며 인사 시스템을 실시간 동기화하는 기능은 아닙니다. 부서명만 바뀌고 코드가 같으면 코드 규칙의 권한은 유지됩니다.

개인 권한과 부서 권한은 합집합입니다. 개인 권한 회수는 부서 권한을 거부하는 예외 규칙이 아니며, 부서 규칙을 회수해도 별도로 승인된 개인 권한은 유지됩니다. 부서 변경은 도구의 revision 조건과 단일 문서 저장으로 처리합니다. 사번 일괄 저장은 일부만 성공할 수 있으므로 결과를 개인별로 나누어 표시하고, 재시도 시 이미 승인된 사번은 다시 추가하지 않습니다.

새 설정값·MongoDB 초기화·기존 데이터 이전은 필요하지 않습니다. 기존 `runtime_config.py`와 업로드 파일은 유지하고 변경한 백엔드·프런트엔드 원본·생성된 `static/app.js`·스타일을 함께 교체합니다.

## 1. 폴더 준비

pt_ai_square 폴더 전체를 복사합니다. index.py, web_main.py, __main__.py, __init__.py, _square_bootstrap.py 등 Python 파일과 templates·static 폴더가 함께 있어야 합니다. 상위 프로젝트나 고정 폴더 이름은 필요하지 않습니다. 업데이트할 때 기존 runtime_config.py와 업로드 저장 폴더를 보존하세요.

## 2. 패키지 설치

web_main.py가 있는 폴더에서 터미널을 엽니다.

```powershell
python -m pip install -r requirements.txt
```

VS Code에서 선택한 Python과 설치에 쓰는 Python이 같아야 합니다. 특정 Python을 사용한다면 아래처럼 같은 실행 파일로 설치합니다. 사내망에서는 회사에서 안내한 pip 저장소 설정을 사용하세요.

```powershell
& "$env:LOCALAPPDATA\Programs\Python\Python311\python.exe" -m pip install -r requirements.txt
```

## 3. 설정 입력

runtime_config.example.py를 같은 폴더의 runtime_config.py로 복사해 값을 입력합니다. .env는 읽지 않습니다. 프로세스 환경변수가 있으면 Python 파일보다 우선합니다.

```python
PTAI_DATA_MODE = 'mongodb'  # 실제 저장. 가짜 화면 확인은 'dummy'
PTAI_AUTH_MODE = 'mock'
PTAI_MOCK_USER = '1000001'
PTAI_MOCK_NAME = '테스트 사용자'
PTAI_MOCK_ADMIN = True
PTAI_COOKIE_SECURE = False
MONGODB_URI = '실제 MongoDB 연결 주소'
MONGODB_DATABASE = '사용할 DB 이름'
# 선택: 업로드 자료를 보존할 절대 경로
# PTAI_DATA_DIR = r'C:\pt_ai_square_data'
```

기본 DATA_MODE='mongodb'에서는 로컬에서도 실제 DB를 사용합니다. 정보를 비워두면 설정을 요청하는 오류가 나오며 예시 데이터로 자동 대체하지 않습니다. 시험용 DB를 운영 DB와 분리하면 운영 자료에 영향을 주지 않고 확인할 수 있습니다. 비밀번호 포함 URI와 세션 키는 Git에 올리지 마세요.

## 샘플 데이터로 화면 확인하기

실제 자료를 바꾸지 않고 목록·순위·상세·등록 관리 화면을 보려면 runtime_config.py의 두 값을 설정합니다.

```python
PTAI_DATA_MODE = 'dummy'
PTAI_AUTH_MODE = 'mock'
```

서버를 종료하고 다시 실행한 뒤 브라우저를 새로고침합니다. 상단에 **샘플 데이터 · 조회 전용**이 표시됩니다. MongoDB 주소가 이미 있어도 연결하지 않으므로 지울 필요가 없습니다. 샘플은 별도 dummy/catalog.json 폴더 파일에서 읽고, 설정 사번은 처음 3개 예시 도구의 등록자로 표시됩니다. 실제 MongoDB나 업로드 폴더는 바뀌지 않습니다.

이 모드는 조회 전용입니다. 업로드·좋아요·수정·승인·실제 다운로드를 누르면 저장하지 않고 안내합니다. 실제 업로드·다운로드·버전 관리 점검은 DATA_MODE를 'mongodb'로 되돌려 재시작하세요. 회사 SSO와 함께 사용하는 모드는 'mongodb'입니다.

| 설정 조합 | 동작 |
|---|---|
| mock + mongodb | 설정 사번으로 접속, 실제 DB·파일 저장 및 버전 관리 |
| sso + mongodb | 회사 SSO 사용자로 접속, 실제 DB·파일 저장 및 버전 관리 |
| mock + dummy | 설정 사번으로 가짜 데이터 화면 조회, DB 연결 및 저장 없음 |

프로세스 환경변수 PTAI_DATA_MODE가 있으면 파일보다 우선합니다. 파일을 고쳤는데 모드가 바뀌지 않으면 실행 환경의 같은 이름 변수를 확인하세요. MongoDB 장애가 발생해도 dummy로 자동 전환하지 않습니다.

## 4. 실행과 종료

```powershell
python index.py
```

VS Code에서 index.py의 **Python 파일 실행**을 눌러도 됩니다. 터미널을 켜 둔 채 표시되는 로컬 주소를 브라우저로 엽니다. Ctrl+C로 종료하고, 설정 변경 후 다시 실행합니다. `web_main.py`는 앱 정의용이며 단독 실행 시 웹 서버를 시작하지 않습니다.

index.py는 회사 기본 코드인 `application.run(debug=True, host='0.0.0.0')`를 그대로 사용합니다. 포트를 지정하거나 Waitress를 자동 선택하지 않습니다. 직접 실행의 debug=True도 유지합니다. 회사 실행기가 `index:application`을 불러올 때에는 이 실행문을 호출하지 않습니다. mock은 SSO 미사용이며 설정 사번으로 동작합니다.

기존 로컬 보조 명령 `python __main__.py run`도 지원합니다. 이 보조 명령만 `PTAI_HOST`·`PTAI_PORT`를 읽으며 기본 로컬 포트는 5080입니다. 회사 기본 실행을 위해 그 값을 바꿀 필요는 없습니다.

## 5. 회사 SSO 및 배포

회사 환경에서 hcputil을 설치한 뒤 PTAI_AUTH_MODE를 'sso'로 바꾸고 HTTPS 환경에서는 PTAI_COOKIE_SECURE를 True로 설정합니다. 기본 관리자 사번은 PTAI_ADMIN_IDS에 쉼표로 구분하고 추가 관리자는 관리자 메뉴에서 지정합니다. 상세 회사 인증 흐름은 HCP_DEPLOYMENT.md를 참고하세요.

회사 기본 진입점은 `index:application`이며, 기존 회사 실행기의 `web_main:app`도 동일한 앱을 제공합니다. 불러오기만 할 때에는 별도 서버를 시작하지 않습니다. 회사의 시작 명령·포트·프록시 설정은 기존 배포 방식대로 유지하세요. 실제 사내 인증은 회사 환경에서 검증해야 합니다. 인증 이후의 저장·권한·버전 API는 SSO 사용과 미사용이 동일합니다.

SSO SDK는 유효한 인증 세션이 없는 `/login`에서만 호출합니다. 로그인 후 서명된 앱 세션은 최대 8시간 유지하며 새로고침·API 호출로 만료 시간을 늘리지 않습니다. 매 보호 요청에서 MongoDB의 계정 활성 상태와 현재 역할·도구 권한을 확인하고 기존 CSRF·API 인증키 검사를 유지합니다. 세션이 만료되면 페이지는 로그인으로 이동하고 API는 401을 반환합니다. 회사 SSO에서만 로그아웃해도 앱 세션은 즉시 취소되지 않으며 플랫폼 로그아웃·세션 만료·DB 계정 비활성화로 접근이 차단됩니다.

## 6. MongoDB와 파일 저장소

| 저장 위치 | 저장 내용 |
|---|---|
| MongoDB | 도구 설명·등록자·조직·업무, 버전·파일명·경로 식별자·크기·해시, 권한, 좋아요·다운로드 이력, 요청·답변·담당자·첨부 정보, 개인 알림 |
| DATA_DIR/artifacts | ZIP·EXE·MSI·PS1 배포 파일 원본 |
| DATA_DIR/request_attachments | 요청에 첨부한 이미지·PDF·문서·ZIP 원본 |

DATA_DIR 기본값은 앱 폴더의 instance입니다. DB와 DATA_DIR을 함께 백업하고 서버 재배포 시 저장 폴더를 보존하세요. 첨부는 인증된 API로 다운로드하며 저장 폴더를 정적 URL로 공개하지 않습니다. 저장 공간 사용량에는 두 파일 폴더가 모두 포함됩니다.

관리자 → 저장 공간의 이전 버전 정리는 배포 파일에 적용합니다. 요청 첨부는 요청과 함께 보관하며 배포 정리로 삭제하지 않습니다. DB 응답이 끊겨 저장 여부가 불명확하면 파일을 보존하므로 장애 복구 후 연결되지 않은 파일은 별도 운영 점검이 필요합니다.

## 7. 실행 후 점검 순서

1. SSO 미사용 표시와 설정한 사번을 확인합니다.
2. 작은 ZIP을 도구 등록으로 게시하고 다운로드해 원본을 확인합니다.
3. 등록 관리 → 버전에서 새 ZIP을 게시해 v2 발급을 확인합니다.
4. 이전 버전으로 복구하고 다운로드 대상이 바뀌는지 확인합니다.
5. 기능 요청에 이미지나 문서를 첨부하고 다운로드합니다.
6. 서버 재시작 후 도구·요청·파일이 유지되는지 확인합니다.

## 8. 배포 파일과 EXE

웹은 파일 형식을 변환하지 않습니다. EXE는 제작자가 만든 완성 파일을 업로드하며 ZIP은 ZIP으로 배포합니다. 일반 Python·Skill·MCP의 자동 EXE 변환은 구현되어 있지 않습니다. 설치·연결 안내는 파일 실행, Skill 폴더 배치, 재시작, MCP URL 연결 등 사용을 시작할 절차를 설명하는 항목입니다.

도구의 **URL 연결** 등록은 HTTP와 HTTPS를 모두 지원합니다. `http://mcp.example.internal:8080/mcp`처럼 호스트와 필요한 포트·경로를 입력할 수 있으며, 주소의 아이디·비밀번호·잘못된 포트·지원하지 않는 프로토콜은 거절합니다. URL은 해당 도구 버전의 연결 정보로 MongoDB에 저장되며 웹 서버가 그 주소를 호출하거나 원격 MCP 설정을 자동 배포하지 않습니다. 새 `runtime_config.py` 옵션이나 데이터 마이그레이션은 필요하지 않습니다. 이는 **등록할 도구의 주소**에 대한 규칙이며, 개인 KEY로 AI SQUARE에 연결할 때의 정확한 HTTP 주소 확인·인증·리디렉션 차단 규칙은 그대로입니다.

### 실제 등록 예시

1. 개발자가 MCP 소스가 담긴 검색도구.zip을 올립니다.
2. 서버가 파일 형식·크기·ZIP 경로 등을 검사하고 v1을 발급합니다.
3. 사용자는 검색도구.zip 원본을 내려받습니다. 검색도구.exe가 만들어지지 않습니다.
4. 개발자가 완성된 설치용 검색도구.exe를 올렸다면 그 EXE 원본을 배포합니다.
5. 다음 파일을 새 버전으로 올리면 v2가 되고 이전 v1로 배포 대상을 복구할 수 있습니다.

배포 번호는 플랫폼의 파일 버전이며 EXE 내부의 프로그램 버전을 다시 작성하지 않습니다. 과거 기획에서 다룬 자동 설치 EXE 생성은 현재 구현과 다릅니다. 현재 Flask 서버에는 NSIS 등의 설치 파일 생성 과정이나 Python 소스 컴파일 과정이 없습니다. EXE 제작은 LLM의 필수 작업이 아니라 별도의 빌드 도구와 유형별 설치 규칙이 필요한 기능입니다. 모든 MCP·Skill·플러그인 파일을 일괄적으로 EXE로 바꾸는 기능은 제공하지 않습니다.

## 9. 오류 확인

최근 기능 갱신 시에도 기존 `runtime_config.py`, `PTAI_DATA_DIR`, MongoDB 주소와 DB 이름을 유지합니다. 사번을 사용자 ID로 계속 사용하므로 기존 도구 등록자·권한·활동 이력은 연결이 유지됩니다. SSO 로그인 시 이름·부서명·부서코드를 갱신하며 DB 전체를 초기화하지 않습니다.

새로고침·관리자 삭제에서 반복되던 SSO 호출 수정에는 새 환경설정이 필요하지 않습니다. 코드 반영 후 기존 회사 프로세스를 같은 시작 명령·포트로 재시작합니다. 기존 세션에는 SSO 인증 표식이 없으므로 한 번 다시 로그인한 뒤 홈 새로고침, API 조회, 관리자 검수용 항목 삭제를 확인합니다. SDK 오류는 `HCP SSO failure stage=... error=...` 로그의 단계·예외 유형으로 확인하고, MongoDB 오류 503은 별도 DB 장애로 점검합니다. 쿠키·인증키·사번·예외 메시지 원문은 로그에 남기지 않습니다.

연결 KEY 정책은 **사번당 활성 키 하나**입니다. 새 키에는 유효기간 선택이 없고 `expires: null`로 저장되어 재발급·사용 취소·계정 비활성화 전까지 사용할 수 있습니다. 기존 기간형 키는 원래 만료일을 유지하므로 기간 제한 없이 사용하려면 재발급합니다. 이미 만료·취소된 키는 되살리지 않습니다. 기존에 여러 키가 있던 계정은 첫 사용·조회 시 아직 유효한 최신 키 하나로 정리됩니다. 재발급하면 기존 키는 즉시 무효화되지만 감사용 발급·사용 기록은 남습니다. `/local-access`에서 현재 상태를 확인하고 연결 프로그램의 키를 교체하세요. 원문 키는 발급 직후에만 표시하며 MongoDB에는 해시를 저장합니다. `users.activeConnectionKeyId`와 `local_tokens.user`를 통해 현재 키와 사번을 연결합니다.

발급 시 화면 새로고침 안내와 400 응답이 나오면 이전 화면이 `days` 값을 보낸 경우입니다. 화면을 새로고침해 기간 선택 없는 새 화면에서 다시 발급합니다. 기존 KEY 기록의 `expires`가 누락되었거나 잘못된 값이면 인증되지 않으므로 재발급으로 교체합니다.

사진은 SSO 모드에서 웹 서버가 사내 사진 서버의 해당 사번 JPG를 읽어 `/api/me/photo`로 전달합니다. 운영 서버에서 사진 서버에 접근할 수 있어야 합니다. 원본 HTTP 주소를 브라우저에 직접 넣지 않아 운영 HTTPS의 혼합 콘텐츠 차단을 피합니다. 사진이 없거나 응답하지 않으면 이름 첫 글자를 표시하며 서비스 이용은 계속 가능합니다. 로컬 mock에서는 사내 사진 서버에 접속하지 않습니다.

- requirements 오류: 실행과 설치에 같은 Python을 쓰는지 확인합니다.
- 상대 import 오류: web_main.py 한 파일만 바꾸지 말고 최신 관련 Python 파일 전체를 갱신합니다.
- MongoDB 오류: URI·DB 이름·네트워크·계정 권한을 확인합니다. 예시 자료나 SQLite로 대체하지 않습니다.
- 주소 사용 중: 같은 앱을 중복 실행했는지 확인하고 본인이 켠 이전 실행을 종료합니다. 회사가 정한 포트나 시작 방식을 임의로 바꾸지 않습니다.

### 9-1. 저장 성공과 후속 작업 재처리

도구를 게시할 때에는 “도구·버전 저장” 외에 “누가 게시했는지 이력 남기기, 자동 구독, 사용자에게 알림 보내기”가 뒤따릅니다. 앞의 저장은 성공했는데 뒤의 알림만 실패한 경우, 이미 저장한 도구를 다시 등록하지 않도록 결과를 나누어 처리합니다.

변경할 원본과 후속 작업 목록(outbox)을 **같은 문서의 한 번의 insert/update**에 저장합니다. 원본 쓰기가 확인된 뒤 후속 작업을 전달하며, 전달과 완료 표시가 끝난 이벤트만 outbox에서 제거합니다. 실패한 이벤트는 DB에 남아 서버 재시작 후에도 재처리할 수 있습니다. 이력·알림은 고유 이벤트 ID로 중복을 막고, 지연된 자동 구독은 사용자가 이미 꺼 둔 구독 설정을 다시 켜지 않습니다. 여러 컬렉션에 걸친 트랜잭션이나 변경 요청 전체의 무제한 재시도를 추가한 방식은 아닙니다.

| 실제 상황 | 화면·운영 확인 |
|---|---|
| 게시·한도·권한 변경 등 저장 성공, 이력·알림만 지연 | 저장 결과를 유지하고 후속 작업을 재처리합니다. 이미 반영된 변경을 반복하지 않습니다. |
| 좋아요 상태 저장 성공, 총 개수 조회 실패 | 선택 상태는 유지합니다. 이전 숫자를 바탕으로 임시 표시하고 다음 정상 목록 조회에서 서버 집계로 갱신합니다. 숫자 조회 실패를 저장 실패로 바꾸지 않습니다. |
| 게시 저장 성공, 화면 갱신만 실패 | 게시 완료와 갱신 실패를 나누어 안내합니다. 등록 관리나 상세 조회로 결과를 확인합니다. |
| 한도 저장 성공 | 서버가 응답한 정책·revision을 바로 표시합니다. 저장 직후 전체 목록을 다시 조회하지 않습니다. |
| 원본 쓰기 실패 또는 응답 유실 | 실제 저장 여부를 먼저 확인합니다. 성공 여부를 모르는 상태에서 등록·삭제 버튼을 연타하지 않습니다. |

저장 요청의 후속 처리는 해당 문서 또는 도구·사용자 범위로 제한합니다. 전체 대기 작업은 `/api/notifications` 알림 조회에서 다시 시도합니다. **홈의 `/api/bootstrap` 목록 조회에서는 후속 쓰기를 실행하지 않습니다.** 브라우저가 열려 있고 요청이 정상 수행되면 약 30초 알림 확인 주기를 이용하고, 숨겨진 탭에서 돌아올 때도 확인합니다. 겹치는 알림 조회와 5초 이내 반복 확인은 합치거나 건너뜁니다. 별도 상주 worker는 없으므로 접속자가 없거나 DB가 계속 실패하면 대기 작업도 남을 수 있습니다.

댓글 작성자의 자동 구독 또는 한 수신자의 알림 쓰기가 실패해도 다른 수신자의 알림 전달은 시도합니다. 실패한 효과가 있으면 원본 outbox를 유지하고, 재처리할 때 이미 전달한 알림을 중복 생성하거나 읽지 않음으로 되돌리지 않습니다. 원본 댓글 저장 실패까지 성공으로 처리하지는 않습니다.

목록 조회는 한 요청에서 필요한 분류·권한·구독·의견·작성자 정보를 묶어서 읽습니다. 요청 간 캐시는 사용하지 않으므로 다음 조회는 변경된 권한을 다시 판단합니다. 현재 사용자가 읽을 수 없는 도구의 의견·버전은 포함하지 않습니다. 버전·의견 전체를 전달하는 기존 응답은 유지하므로 대규모 데이터의 전송량까지 일정해지는 것은 아닙니다.

일반 outbox 대상은 `tools`, `access`, `feedback`, `ideas`, `administrators`, `settings`, `taxonomy`, `users`입니다. 컬렉션당 최대 50개 문서·문서당 최대 50개 이벤트를 전달하고, 좋아요·다운로드 활동은 한 번에 최대 50개 상태 문서를 재처리합니다. 이전 버전의 `postCommit` 대기 작업도 호환 처리합니다. 이 제한이 모든 요청의 처리 시간 상한을 보장하는 것은 아닙니다. 한 이벤트가 실패해도 다른 이벤트 전달은 시도합니다.

연결 KEY 발급·취소는 사용자 문서의 활성 KEY 포인터와 이력을 같이 저장합니다. 이전 KEY의 취소·교체 표시가 후속 처리로 남아 있어도 실제 인증은 현재 활성 포인터와 일치해야 합니다. KEY 원문은 outbox에 넣지 않습니다. 다운로드의 원본 상태 저장이 성공했다면 이력·자동 구독 전달 실패만으로 파일 응답을 막지 않습니다. 원본 저장 실패까지 무시하지는 않습니다.

요청 첨부 등록이 실패하면 DB 참조를 확인하여 미참조가 확인된 파일만 정리합니다. 이미 참조되었거나 DB 조회 실패로 참조 여부를 확인하지 못한 파일은 보존합니다. 파일 삭제 자체가 실패해도 원래 등록 오류를 유지하고 로그에 남깁니다. 보존된 미참조 파일을 자동으로 주기 청소하는 기능은 없으므로 장애 후 운영 점검이 필요합니다.

화면에서는 같은 오류를 빨간 경고와 파란 상태 메시지로 중복 표시하지 않습니다. 수정·승인 등에서도 변경 응답을 받은 뒤 목록·상세 조회만 실패하면 변경이 저장됐다는 점을 함께 안내합니다. 원본 변경 요청이 실패한 경우와 구분하여 결과를 확인합니다. 같은 도구가 여러 카드에 보여도 좋아요 요청은 한 번씩 처리하며, 오래된 목록 응답은 더 최신 결과를 덮어쓰지 않습니다. 웹 게시의 동일 내용·파일·대상 재시도는 같은 요청 ID를 사용합니다. 페이지를 닫거나 새로고침한 뒤까지 그 ID를 영구 보관하지는 않으므로, 응답이 유실됐다면 등록 결과를 먼저 확인합니다.

운영자는 다음 순서로 반영·확인합니다.

1. 기존 `runtime_config.py`, MongoDB 데이터, `PTAI_DATA_DIR`의 파일을 보존합니다. 별도 DB 초기화나 자료 삭제는 하지 않습니다.
2. `config.py`를 포함한 최신 프로그램 코드와 `frontend`·`static` 파일을 함께 교체합니다. 실제 `runtime_config.py`를 예시 파일로 덮어쓰지 않습니다.
3. 회사 기존 절차로 모든 웹 작업 프로세스를 재시작하거나 교체합니다. `index.py`·SSO 방식·시작 명령·포트를 임의로 바꾸지 않습니다.
4. 브라우저에서 Ctrl+F5를 누르고 검수용 등록·좋아요·저장 한도를 한 번씩 확인합니다. 화면을 다시 조회한 뒤에도 결과가 유지되는지 봅니다.
5. 후속 작업이 남으면 `MongoDB follow-up deferred` 로그와 해당 문서의 outbox·이전 postCommit을 확인합니다. 원본 저장 오류는 문의 번호, HTTP method, route 템플릿, retry_writes와 MongoDB 숫자 코드로 구분합니다.

### 9-2. MongoDB 연결을 읽기 전용으로 진단하기

`web_main.py`가 있는 폴더에서 웹 앱과 같은 Python으로 실행합니다.

```powershell
python scripts/diagnose_mongo.py
```

웹과 같은 연결 옵션 생성 함수를 사용해 ping·hello·buildInfo만 요청합니다. DB·문서 생성이나 데이터 쓰기는 하지 않습니다. 접속 주소·계정·비밀번호·세션 ID·원문 서버 오류를 출력하지 않습니다. **ping 성공은 등록·수정 권한이나 모든 쓰기의 성공을 보증하지 않습니다.** 진단은 별도 프로세스이므로 웹 서버를 재시작하지 않았다면 진단과 웹이 다른 설정을 사용 중일 수 있습니다.

기존 `runtime_config.py`는 그대로 사용할 수 있습니다. 선택 설정 `PTAI_MONGODB_RETRY_WRITES`는 없으면 False이며 URI의 retryWrites보다 우선합니다. 자동 쓰기 재시도를 끄는 것이고 쓰기 결과 확인·읽기 재시도를 끄지는 않습니다. 코드 225는 같은 DB 세션의 요청 번호 순서가 맞지 않는 `TransactionTooOld`입니다. 기존 자료가 오래됐다는 뜻이 아니며 DB를 지우거나 인증 모드를 바꾸지 않습니다. 현재 진단 이름 `DB-SESSION-ORDER`는 운영 보고서의 `DB-TRANSACTION-ORDER`와 같은 225를 뜻합니다.

2026-10-23 사용자 제공 운영 진단은 `retryWrites=false`, `ping=ok`, `maxWireVersion=13`, `sessionsSupported=true`, `replicaSet=true`, `router=false`, `version=5.0.11-10`이었고 수정 후 정상 실행됐다는 확인이 있었습니다. 이는 사용자 제공 관찰이며 개발 환경에서 해당 회사 DB를 직접 검증한 결과는 아닙니다. 버전 문자열만으로 제품이나 오류 원인을 확정하지 않습니다. 상세 해석과 추가 점검은 `SSO_OPERATIONS_GUIDE.md` 13-2·13-3절을 참고하세요.

## 10. Skill 배포 정보 연계

코드 변환이나 EXE 생성 없이 ZIP 최상위 ai-square.json을 읽습니다. Skill에는 준비 스크립트와 예시, 웹과 같은 Python 검사 규칙을 배포합니다. 검사 API는 POST /api/packages/inspect이며 로그인·CSRF 확인 뒤 임시 업로드를 검사하고 파일을 삭제합니다. 게시 API는 미리보기 결과를 신뢰하지 않고 실제 ZIP을 다시 검사합니다.

배포 정보는 MongoDB tools 문서의 각 `versions[].package`에 원본 선언 그대로 저장합니다. 파일은 `DATA_DIR/artifacts`에 원본 그대로 보관합니다. 기존 자료에 일괄 이전은 필요 없습니다. 배포 정보가 없는 기존 파일은 수동 입력을 유지합니다. 명시적으로 선택한 기존 도구의 새 버전은 ZIP의 packageId가 달라도 게시할 수 있습니다.

서버가 발급하는 숫자 `toolId`와 플랫폼의 고정 `packageId`는 새 버전에서도 유지됩니다. `tools.packageId`는 최초 정상 배포 선언의 값을 저장하며, 이전 데이터는 첫 정상 선언을 계산해 읽고 다음으로 성공한 도구 변경의 동일 CAS 쓰기에서 기록합니다. 정상 선언이 한 번도 없었다면 처음 선언을 읽는 버전에서 정착합니다. 과거 버전·롤백·파일 삭제는 이 값을 바꾸지 않습니다. `packageId`는 전역 유일 DB 키가 아닙니다.

도구·manifest·게시 결과·초안 API의 최상위 `packageId`는 플랫폼의 고정 값이고, `sourcePackageId`는 해당 버전 원본의 값입니다. `packageIdentityChanged`는 두 값이 다름을 알리는 표시이며 승인 생략용 값이 아닙니다. `versions[].package.packageId`와 배포 JSON의 `package.packageId`는 원본 선언을 유지합니다. 클라이언트 metadata로 고정 ID를 바꿀 수 없습니다. ZIP 재작성은 하지 않으므로 업로드·다운로드의 해시도 같습니다. 메타데이터 검사 실패 시 수동 등록과 소유권·권한·revision·파일 검사는 유지합니다.

`/api/publish-targets?packageId=...`는 고정 ID로만 후보를 찾습니다. 새 파일의 다른 식별자를 기존 도구의 자동 별칭으로 사용하지 않습니다. MCP·배포 Skill은 명시한 도구 ID를 우선하고, 대상이 없으면 고정 ID 또는 이름 검색으로 본인 도구 후보를 보여줍니다. 이름 유사성만으로 업데이트하지 않습니다. KEY 게시의 웹 승인·파일 해시·24시간 초안·재전송 중복 방지 검사는 그대로 적용됩니다. 서버 소스와 최신 MCP ZIP·배포 Skill·브라우저 app.js를 함께 배포하고, 기존 운영 설정·DB·업로드 저장소는 보존하세요.

GET /api/tools/{id}/releases/{n}/deployment는 해당 배포의 ID·번호·SHA-256·크기·파일 주소·버전 확인 주소·원본 배포 선언·게시 당시 설치 안내를 JSON으로 제공합니다. 별도의 파일 저장 공간을 사용하지 않고 요청 시 생성합니다. 기존 도구 조회 권한을 적용하며 삭제·철회된 버전은 제공하지 않습니다. 현재 배포 manifest API에도 연결 주소를 포함하고, 롤백하면 해당 버전의 선언으로 돌아갑니다.

자동 입력은 사람의 검토를 돕는 기능입니다. 실제 패키지 호환성, 의존성 설치 가능 여부, 실행 성공과 악성코드 여부는 검사하지 않습니다. 실행 시 버전 확인과 SSO 인증 클라이언트 연결은 제작자가 별도로 구현해야 하며 배포 정보 JSON만으로 자동 완성되지 않습니다. 설치된 버전은 실제 설치가 끝난 뒤 기록하고 서버 최신 번호로 매번 덮어쓰지 마세요.
## 관리자 화면에서 파일 저장 한도 변경

**관리자 → 저장 공간**에서 플랫폼 파일 사용량, 파일 저장 디스크의 남은 공간, 현재 추가 저장 가능량을 확인합니다. **새로고침**으로 다시 조회할 수 있으며 화면 진입·업로드 때도 현재 상태를 확인합니다.

1. **직접 지정**을 선택하면 이 플랫폼에 사용할 최대 용량을 GB로 입력합니다. 예: 20GB. 실제 디스크가 더 작으면 디스크의 남은 공간에 맞춰 업로드가 제한됩니다.
2. **서버 여유 공간에 맞추기**를 선택하면 운영체제가 보고하는 남은 공간을 기준으로 계산합니다.
3. **서버에 남겨둘 여유 공간**을 입력합니다. 예: 10GB. 디스크에 100GB가 남아 있으면 자동 모드의 추가 저장 가능량은 약 90GB입니다. 다른 프로그램이 30GB를 쓰면 약 60GB로 줄어듭니다.
4. **한도 저장**을 누릅니다. MongoDB의 settings/storage_limits에 저장되며 재시작 없이 다음 업로드에 적용됩니다. 보관 정책과는 별도입니다. 한도를 낮춰도 기존 파일은 자동 삭제하지 않습니다.

GB는 1,024MB 기준입니다. 관리자가 처음 저장하기 전에는 runtime_config.py의 `PTAI_STORAGE_QUOTA_MB`(기본 5120MB)와 `PTAI_STORAGE_RESERVE_MB`(기본 1024MB)를 사용합니다. 관리자 화면에서 저장한 이후에는 해당 MongoDB 설정이 우선합니다. 설정 변경 이력에는 변경한 관리자를 기록하며 동시에 수정한 경우 다시 조회하도록 안내합니다.

파일 저장소의 artifacts와 request_attachments가 플랫폼 사용량에 포함됩니다. 같은 디스크의 OS·로그·다른 서비스·로컬 MongoDB는 디스크의 전체 사용량에는 포함되지만 플랫폼 파일 사용량에는 포함되지 않습니다. 원격 MongoDB 서버·다른 드라이브·다른 마운트의 용량을 자동 합산하지 않습니다. 컨테이너/네트워크 저장소의 별도 할당량은 운영체제의 디스크 조회값과 다를 수 있으므로 운영 환경에서 확인합니다.

업로드 시작과 저장 중 여유 공간을 검사합니다. 공간 부족이나 디스크 조회 실패 시 새 업로드를 중단하고 임시 파일을 정리합니다. 기존 파일 조회·다운로드와 URL/명령어 등록은 유지합니다. HTTP 요청 파싱 중의 임시 업로드 공간은 파일 저장소 한도와 별도로 웹 서버 설정으로 관리합니다.

단일 앱 프로세스에서는 쓰기 잠금으로 동시에 저장하는 파일의 한도를 확인합니다. 여러 프로세스나 여러 서버가 하나의 저장소를 공유하는 경우 정확한 공용 최대 용량 강제에는 파일시스템의 quota 설정을 병행하세요. 자동 모드는 서버 디스크를 증설하거나 파일을 자동 삭제하는 기능이 아닙니다.


## AX Workspace 자료실 및 관리자 삭제 기능

AX Workspace 탭은 관리자가 완성된 설치 파일·ZIP·확장 프로그램을 직접 등록하는 자료실입니다. 화면 분류는 **전체 / AX Workspace / 확장 프로그램 / 연동 도구**입니다. 특정 확장을 웹 코드에 내장해 제공하지 않습니다. 관리자는 **AX Workspace → 파일 등록**에서 이름·설명·분류와 파일을 등록하고, 사용자는 등록된 카드에서 다운로드합니다. 배포 번호는 서버가 v1부터 자동 발급합니다. 등록한 파일은 원본 그대로 전달되며 웹이 EXE를 ZIP에 삽입하거나 서버 주소를 주입하지 않습니다.

프로그램에 `connection.json` 같은 연결 파일이 필요하면 배포자가 프로그램의 설치 규격에 맞춰 완성된 ZIP에 포함한 뒤 업로드합니다. 실제 연결 KEY는 파일에 넣지 않고 사용자가 해당 프로그램에서 입력합니다. 기존 AX 자료, MongoDB의 메타데이터와 업로드 저장소는 그대로 유지합니다.

P&T AI Square 연결 확장의 직접 등록 예시는 **배포자: 서버 주소가 포함된 확장 ZIP 준비 → 관리자: AX Workspace의 파일 등록 → 사용자: 지원 앱의 설정 → 추가 기능 → 확장 ZIP 가져오기 → 개인 KEY 입력**입니다. 사용자는 압축 해제 없이 ZIP을 선택하고 이름·서버 주소·설치 위치를 검토합니다. HTTP 서버는 비암호화 연결 안내도 확인합니다. 앱에 ZIP 가져오기 메뉴가 없다면 이를 지원하는 공통 앱 설치 파일을 별도로 배포해야 하며, 확장 ZIP만 등록해서 기존 앱에 메뉴가 생기지는 않습니다. 확장 자체에는 설치 EXE를 넣지 않습니다. EXE를 제외한 것과 V3 검증 완료는 별개이며, 실제 사내 PC에서의 차단 해소 여부는 아직 확인되지 않았습니다.

웹은 이 예시를 위한 전용 확장 UI나 설치 파일을 내장하지 않습니다. AX Workspace 다운로드는 업로드 원본을 그대로 전달합니다. KEY 발급·재발급과 별도 로컬 MCP의 서버 주소·다운로드 폴더 자동 설정은 기존대로 제공하며, `PTAI_PUBLIC_URL`로 AX 등록 파일의 내용을 수정하지 않습니다.

기존 SSO/mock 사번과 관리자 설정을 그대로 사용합니다. 새 환경변수나 DB 초기화는 필요하지 않습니다. `backend/ax_workspace.py` 블루프린트를 기존 `init_app`에 추가하며 회사의 `index.py`/`web_main.py` 실행 방식·포트를 변경하지 않습니다.

- AX Workspace 메타데이터와 버전 기록: MongoDB `workspace_files`. 원본 파일: 기존 `DATA_DIR/artifacts`. 이전 버전의 파일도 보존하며 기존 저장 용량 한도에 포함됩니다.
- 파일 등록은 관리자 세션과 CSRF 확인을 거칩니다. 목록·다운로드는 로그인 사용자에게 열립니다. 개인 연결 KEY의 API 허용 목록에는 추가하지 않았습니다.
- 독립된 프로그램은 **파일 등록**, 기존 프로그램의 갱신은 **해당 카드 → 새 버전 등록**을 사용합니다. 새 버전은 같은 카드 ID에 연결하고 `expectedRevision`으로 동시 변경을 검사합니다. 게시가 성공하면 `release`가 1씩 증가하여 v2·v3으로 표시되며, 클라이언트의 수동 `version`/`release` 값으로 번호를 바꿀 수 없습니다. 새 파일을 별도 카드로 등록하면 기존 카드의 구독자에게 업데이트 알림을 보내지 않습니다.
- 기존 AX 데이터의 파일·구독·버전 이력은 유지합니다. 화면/API의 배포 번호는 `release` 기준으로 표시하고 과거 이력에 저장된 수동 버전은 보존합니다. 기존 `other` 분류는 조회·입력 시 `integration`(연동 도구)으로 정규화하며 DB 일괄 이전은 하지 않습니다. `plugin`의 화면 이름만 확장 프로그램으로 바뀝니다.
- AX 다운로드 GET 요청은 현재 사번의 알림을 자동 구독합니다. 구독은 MongoDB `workspace_subscriptions`에 별도로 저장하며 일반 도구 다운로드 수·구성원 순위와 분리합니다. 카드에서 명시적으로 끈 구독은 재다운로드로 다시 켜지지 않습니다. HEAD 요청은 구독을 만들지 않습니다.
- 버전 메타데이터와 알림 outbox를 같은 `workspace_files` 문서에 원자적으로 저장합니다. 원본 저장 이후 알림 전달만 실패하면 새 버전 저장을 취소하지 않고 대기 작업을 남겨 재시도하며 중복 알림을 만들지 않습니다. 이전 파일은 보존합니다.
- 업데이트 알림의 대상은 `workspace`이며 종 아이콘에서 누르면 해당 AX 카드로 이동합니다. 웹 화면이 보이는 동안 기존 약 30초 알림 조회를 사용합니다. OS 푸시·CUBE 발송은 제공하지 않으며, 접속이 없거나 DB 후속 처리가 지연되면 즉시 전달을 보장하지 않습니다.
- 기능 적용 이전에는 AX 다운로드 구독 이력이 없었으므로 기존 사용자를 추정해 일괄 구독하지 않습니다. 기존 다운로드 사용자는 파일을 다시 받거나 카드에서 알림을 켜야 합니다. 기존 데이터·`runtime_config.py`를 유지하며 `workspace_subscriptions` 컬렉션과 인덱스는 앱 초기화 때 준비합니다. DB 초기화나 수동 데이터 이전은 필요하지 않습니다.
- 기능 요청 삭제와 도구 영구 삭제는 관리자만 실행합니다. 요청 revision을 검사하고, 도구는 먼저 휴지통으로 이동해야 영구 삭제할 수 있습니다.
- 삭제가 시작된 문서는 수정·복원을 차단합니다. `deletion_jobs`에 정리 작업을 남기고 파일·관련 데이터 정리 후 본문을 삭제합니다. 장애 시 관리자 휴지통의 재시도로 남은 작업을 처리합니다. 최소 삭제 감사 이력과 작업 식별자는 남습니다.
- 다른 도구나 AX Workspace가 함께 참조하는 파일은 지우지 않습니다. 기존 MongoDB 데이터와 `runtime_config.py`, 업로드 저장소를 보존하여 코드만 업데이트합니다.

배포에는 새 backend 및 frontend 파일, 조립된 `static/app.js`, `static/workspace.css`, dummy 자료와 빌드 스크립트를 함께 반영합니다. 앱을 재시작한 뒤 브라우저를 새로고침합니다. 운영 MongoDB 계정은 새 컬렉션 조회·쓰기 및 인덱스 생성을 허용해야 합니다. 테스트는 별도 로컬 MongoDB와 임시 파일로 수행하며 회사 SSO 자체의 실서비스 연동 검증과는 구분합니다.

영구 삭제 완료 뒤 늦게 끝난 작업이 관련 정보를 다시 남기는 경우에 대비해, 알림 조회 때 완료된 삭제 작업 기록을 최대 5개씩 순환 점검합니다. DB 오류가 지속되면 즉시 정리를 보장하지 않으므로 관리자 휴지통의 재시도와 서버 로그를 함께 확인합니다. 별도 상주 작업 프로세스는 추가하지 않습니다.

## ZIP 게시 시 Failed to fetch가 나타날 때

로컬에서 `python index.py`로 실행하면 회사 기본 형식의 `debug=True`를 유지합니다. 실행 환경에 `watchdog`가 설치되어 있으면 Werkzeug 자동 재시작 감시기는 Python 코드뿐 아니라 ZIP 생성·변경·삭제도 감지합니다. 앱 내부에 저장한 업로드 ZIP 또는 배포 정보 미리보기용 임시 ZIP 때문에 서버가 요청 처리 중 재시작할 수 있습니다. 이 경우 파일이나 DB 기록은 저장됐지만 브라우저는 응답을 받지 못할 수 있습니다. 로그의 `Detected change in ...artifacts...zip, reloading`이 이 원인을 구분하는 근거입니다. 모든 네트워크 오류가 이 원인은 아닙니다.

`index.py`는 `backend/dev_reload.py`를 통해 실제 `DATA_DIR/artifacts`와 `DATA_DIR/request_attachments`만 자동 재시작 감시에서 제외합니다. 회사의 진입점, 호스트, 포트와 debug 설정은 유지하며 일반 Python 코드 변경 감시는 계속 동작합니다. 별도 실행기가 자체 파일 감시를 사용하는 경우에는 그 실행기의 감시 제외 설정도 확인해야 합니다.

게시 응답이 끊기거나 잘못된 서버 응답이 오면 화면은 같은 사번·게시 요청 번호의 저장 결과를 `GET /api/publish-requests/{UUID}`로 최대 3회 확인합니다. 각 조회는 최대 4초이며 조회 사이에 짧은 대기를 둡니다. 이 조회는 파일 업로드, 이력 전달 또는 DB 쓰기를 하지 않습니다. 저장된 도구 ID와 버전을 확인한 경우에만 게시 완료로 표시합니다. 확인되지 않는 것은 실패 확정이 아닙니다. 원래 요청이 진행 중일 수 있으므로 입력과 파일을 유지하고 결과 미확인 안내를 보여줍니다.

파일을 자동 재전송하지 않습니다. 사용자가 다시 게시를 누르면 먼저 이전 결과를 조회하고, 결과가 아직 없을 때 같은 요청 번호로 재시도합니다. 내용·파일·등록 대상이 바뀌면 새로운 요청 번호를 만듭니다. 페이지를 새로고침하거나 닫으면 이 임시 요청 정보는 사라지므로 그 경우에는 등록 관리에서 먼저 기존 게시 여부를 확인하세요. 개인 KEY는 이 웹 전용 결과 조회 API를 사용할 수 없습니다.

적용 시 `index.py`, `backend/dev_reload.py`, `backend/mongo_api.py`, `frontend/frontend_api.js`, `frontend/frontend_publish.js`, 조립된 `static/app.js`를 함께 반영합니다. 기존 `runtime_config.py`, 업로드 파일과 MongoDB는 유지합니다. 웹 프로세스를 다시 시작하고 브라우저에서 Ctrl+F5로 새 스크립트를 읽으세요. 별도 운영 패키지 설치나 DB 초기화는 필요 없습니다.

## 개인 KEY만 입력하는 로컬 MCP 연결

개인 연결 KEY는 **조회·다운로드·좋아요·본인 도구 신규 등록·새 버전 게시**를 한 가지 권한으로 제공합니다. 새 KEY의 내부 권한 값은 `publish`이며, 기존 유효한 `read` KEY도 서버에서 같은 유효 권한으로 해석합니다. 웹의 권한 선택은 제거하며 기존 사용자의 재발급·DB 마이그레이션은 필요 없습니다. 인식하지 못하는 권한 값, 만료·취소·비활성 사용자·활성 KEY 포인터 불일치는 계속 거절합니다. 관리자 KEY도 다른 사람의 도구를 수정하거나 삭제·권한 관리·관리자 설정·다른 KEY 발급 API를 호출할 수 없습니다. 웹 세션과 KEY 모두 실제 도구 조회 권한을 검사하며, 신규/버전 게시의 본인 웹 승인 초안 절차는 유지합니다.

조회수는 `POST /api/tools/{id}/view`에 빈 JSON `{}`을 보냈을 때 기록합니다. 같은 사번·도구당 웹과 연결 프로그램을 합쳐 30분에 한 번만 집계하며 MongoDB `activity_state`에 사용자·도구별 상태 문서 하나를 유지합니다. 검색·상세 정보 GET·설치 계획 조회는 조회수를 기록하지 않고, 조회수는 좋아요·다운로드 기반 순위 점수에 더하지 않습니다.

웹의 **열쇠 아이콘 → 내 PC에서 시작하기**에는 **확장 프로그램으로 연결하기**와 **MCP로 연결하기**를 위아래로 항상 표시합니다. 확장 프로그램은 관리자 등록 자료가 있는 AX Workspace 탭으로 안내하고, MCP에는 **로컬 MCP 받기**와 **MCP 설치 안내서**를 제공합니다. 각 연결 절차는 기본으로 접혀 있으며 필요할 때 펼쳐봅니다. Skill 연결 안내는 이 페이지에서 제거하지만 웹 상단의 배포 Skill과 기존 Skill 패키지·기능은 유지합니다. MCP 1.4.0부터 기본 순서는 Python 3.11 이상과 지원 AI 준비 → 웹 ZIP 다운로드·압축 해제 → AI에 최초 한 번 MCP 등록 → 채팅에서 “AI SQUARE 연결해줘” 요청 → 주소·기록 안내를 확인하고 채팅으로 KEY 전달 → 필요한 HTTP 동의 → 실제 계정 인증 확인입니다. 최초 MCP 등록은 별도이며, 설치 안내서에 Claude Code에 설치를 요청하는 예시도 제공합니다.

**로컬 MCP 받기**는 로그인한 사용자의 다운로드 요청에 맞춰 서버 주소가 포함된 ZIP을 제공합니다. `GET /local-access/mcp.zip`과 기존 `/static/guides/pt-square-mcp.zip` 웹 주소는 같은 다운로드 처리를 사용합니다. 저장소에 보관하는 공통 ZIP 자체는 변경하지 않고, 응답 ZIP의 `pt-square-mcp/connection.json`에 `schemaVersion: 1`, `baseUrl`만 추가합니다. KEY·사번·쿠키·MongoDB 접속 정보는 넣지 않습니다. 응답은 개인 캐시에 남지 않도록 `private, no-store`로 제공하며 KEY API의 허용 목록은 늘리지 않습니다.

기본 연결 주소는 현재 웹 요청의 HTTP(S) 주소를 사용합니다. 다운로드 쿼리나 `X-Forwarded-Host`, `X-Forwarded-Proto` 값을 직접 신뢰하지 않습니다. 역방향 프록시의 내부 주소와 사용자가 접속하는 외부 주소가 다를 때만 운영자가 기존 `runtime_config.py`에 선택 설정 `PTAI_PUBLIC_URL`을 추가합니다. 값에는 실제 사용자 접속 주소의 `http://` 또는 `https://`, 호스트, 필요한 포트까지만 넣고 경로·쿼리·인증정보는 넣지 않습니다. 기본값은 빈 문자열이며 현재 배포 주소가 정상적으로 들어간다면 새 설정은 필요 없습니다. 이 값은 로컬 MCP 다운로드에 포함할 연결 주소를 지정하며 웹 실행 포트나 진입점을 바꾸지 않습니다. AX Workspace 자료실에 등록한 파일에는 적용되지 않습니다.

이전의 `/local-access/workspace-extension.zip`과 `/static/guides/ax-workspace-extension-setup.exe` 주소는 로그인 후 AX Workspace 탭(`/?view=ax`)으로 이동합니다. 해당 주소에서 고정 EXE나 서버 주소를 넣은 확장 ZIP을 생성하지 않습니다. 운영 코드 교체 시 예전 `static/guides/ax-workspace-extension-setup.exe`는 배포 대상에서 제외하고, 프로그램이 준비되면 관리자가 AX Workspace 탭에 직접 등록합니다. `organization-store/` 개발 소스는 보존하며 상세 제작 안내는 해당 폴더의 README를 참고하세요.

Windows 사용자는 MCP 등록 후 `connect_account`로 연결을 시작합니다. KEY 없이 호출하면 사이트 주소·KEY 입력 안내·채팅 기록 안내를 반환합니다. 사용자가 일반 채팅에 전달한 KEY는 도구의 `key` 인자로 받아 별도 입력창 없이 `/api/integration/me`로 실제 인증한 뒤 DPAPI로 암호화해 저장합니다. 반환값은 인증 결과의 필요한 계정·연결 정보만 포함하며 KEY를 결과·오류에 다시 출력하지 않습니다. KEY는 대화·모델 입력·도구 호출 입력 기록에 남을 수 있으며, 로컬 DPAPI 저장이 호스트의 기록을 지우거나 KEY를 모델에서 격리하지 않습니다. 일반 MCP 폼 elicitation으로 KEY를 요청하지 않습니다. 기록을 원하지 않는 사용자는 `Connect.cmd`의 가려진 입력란이나 `python run_mcp.py setup`의 숨김 입력을 수동 대안으로 사용할 수 있습니다.

최초 설정이 없으면 `connection_status`가 `CONNECTION_SETUP_REQUIRED`, `connectTool: connect_account`와 해당 사이트의 KEY 발급 링크를 반환합니다. 최초 연결은 웹 ZIP의 주소를 사용하고, 기존 연결은 ZIP과 다른 주소여도 현재 설정의 주소를 유지합니다. 기존 `reconnect_key`도 같은 채팅 입력 절차를 사용합니다. HTTP 주소는 정확한 해당 origin에 대한 비암호화 전송 동의가 있어야 인증 요청을 보냅니다. 기존 저장된 동일 origin의 동의를 재사용하고, 새 동의는 `accept_http_origin` 인자 또는 지원 호스트의 boolean `acceptHttp` HITL로 확인합니다. HITL 미지원이면 `httpApprovalRequired`를 반환해 AI가 채팅에서 동의를 받은 뒤 정확한 주소를 전달하도록 합니다. KEY 입력을 받는 HITL 폼은 만들지 않으며 AI가 사용자 동의를 추정하면 안 됩니다. HTTP 동의가 전송 암호화를 제공하지는 않습니다.

연결 복구만으로 설치·업로드를 재실행하지 않습니다. 인증 실패·저장 전 취소 시 기존 정상 설정을 보존하고, 인증 도중 연결 설정이 바뀌면 이전 요청의 저장을 차단합니다. 이미 시작하거나 완료한 저장은 늦은 취소로 되돌린다고 보장하지 않습니다. 이 기능은 로컬 stdio를 사용하며 추가 HTTP 서버나 포트를 열지 않습니다. 401 복구 링크는 현재 설정의 사이트 `/local-access`를 사용하며, KEY 재발급 시 이전 KEY ID에 묶인 게시 초안은 다시 만들고 웹에서 승인합니다.

일반 setup에는 `--url`과 `--workspace`가 필요 없습니다. 웹에서 받은 주소를 읽고 기본 다운로드 폴더를 자동 생성합니다. 공통 소스 ZIP에는 주소가 없으므로 처음 연결할 때는 웹 다운로드를 사용하거나 개발자가 `--url`을 명시합니다. 다운로드는 기본 폴더 아래 `server-서버식별자/tool-도구ID/v버전`으로 분리해 서로 다른 서버의 같은 도구 번호를 혼동하지 않도록 합니다. 파일을 받는 경로와 실제 설치 범위는 별개이며, 프로젝트/내 계정 설치 선택은 계속 확인합니다.

업로드 원본 또는 설치할 프로젝트가 기존 허용 범위 밖이면 MCP의 `select_workspace`가 PC의 폴더 선택 창을 엽니다. 사람이 직접 선택한 기존 폴더만 허용하며 취소 시 범위를 추가하지 않습니다. 드라이브 전체는 허용하지 않습니다. 기존에 명시적으로 허용한 폴더는 같은 사이트에 다시 연결할 때 유지합니다. 고급 CLI의 `--workspace`는 추가 폴더 설정에만 필요합니다.

`--token-from-env`는 KEY를 암호화 저장하는 옵션이 아닙니다. MCP 실행 프로세스가 `PTAI_API_TOKEN` 환경변수를 매번 읽는 자동화용 방식이므로 일반 Windows 연결에는 사용하지 않습니다. 기존 KEY 형식·MongoDB 매핑·도구·버전·업로드 자료는 유지하고 일괄 재발급하지 않습니다. 새 KEY를 저장하면 다음 MCP 작업에서 갱신된 설정을 읽습니다. MCP 코드 자체를 교체한 경우에는 사용하는 AI 프로그램을 재시작합니다. Claude의 `Connected` 표시는 stdio 통신이며 실제 계정 인증은 `connect_account` 또는 `connection_status` 결과로 확인합니다.

배포 시 웹의 `backend/mcp_package.py`, `backend/local_access.py`, 설정 로더·예시, `templates/local_access.html`, MCP 원본과 새 `static/guides/pt-square-mcp.zip`, 관련 가이드를 함께 반영합니다. 회사의 실행 방식·SSO·포트와 기존 비공개 설정·저장소를 유지합니다. 새 사이트 ZIP의 주소 확인 → KEY 입력 → 사용자 정보 표시 → 자동 폴더로 검색·다운로드 순서로 검수합니다. 운영 서버에 MCP SDK를 설치하거나 DB를 초기화할 필요는 없습니다.

## 등록자 이름으로 도구 검색

웹 검색과 MCP/API `/api/catalog?q=...` 검색은 도구 이름·태그·설명 외에 실제 등록자 이름과 등록 정보의 담당자 이름도 확인합니다. 실제 등록자는 `tools.owner`가 가리키는 현재 `users.name`으로 찾고, 수정 가능한 `data.owner` 담당자 표시와 구분합니다. 계정 이름 조회는 한 번에 처리하며 도구마다 계정을 다시 읽지 않습니다. 등록자 이름으로 찾더라도 비공개 상세·파일 권한은 열리지 않으며 삭제·영구 삭제 진행 중인 도구는 결과에서 제외합니다. 추천의 조직 선호와 실시간/누적 집계 방식은 유지합니다.
