# P&T AI SQUARE 파일 배포 준비

사용자가 만든 도구를 다른 동료가 이해하고 설치·연결할 수 있는 공유 자료로 정리한다. 파일 준비와 API 게시 프로그램이 함께 포함되어 있다. 사용자가 “플랫폼에 등록해줘”라고 요청하면 아래 게시 절차까지 진행한다. 등록 요청이 없으면 준비 단계에서 마친다. EXE 자동 변환이나 사용자 PC 설치를 수행하는 기능은 아니다.

## 개인 인증키로 플랫폼에 등록하기

`scripts/publish_client.py`와 `scripts/square_client.py`가 함께 포함되어 있으므로 다른 Skill을 추가로 받을 필요가 없다. Python 3.11 이상이며 별도 pip 의존성이 없다. 상대 경로 예시는 이 Skill 디렉터리를 기준으로 절대 경로로 실행한다.

1. 이 문서의 배포 준비 절차로 파일과 설치 안내를 만든다. 실제 도구의 유형을 판별해 ai-square.json 또는 별도의 등록 JSON에 적는다. ZIP이면 서버가 선언을 읽어 이름·설명·유형·설치 안내를 채운다. 단일 MD는 ZIP으로 바꾸지 않고, 내용을 읽어 이름·설명·유형 Skill·설치 안내를 별도 JSON에 작성한다.
2. 서버 설정이 없으면 사용자에게 주소를 확인하고 `python scripts/square_client.py configure --url 서버주소`로 설정한다. 다른 프로젝트나 사번의 주소를 추측하지 않는다.
3. 인증은 **업로드 포함** 권한의 개인 키를 해당 터미널 세션의 `PTAI_API_TOKEN`으로 전달하거나 `--authenticate`의 숨김 입력을 사용한다. 유효한 기존 키가 있으면 그대로 사용한다. 키가 없거나 401이면 프로그램이 `/local-access`를 기본 브라우저에 열고 주소를 반환한다. 브라우저가 열리지 않으면 해당 링크를 보여준다. 사용자에게 상단 KEY 아이콘 → **업로드 포함** 선택 → **연결 KEY 발급**을 안내한다. 새 KEY에는 유효기간 설정이 없다. 사번당 활성 키는 하나이며 **KEY 재발급** 시 이전 키는 즉시 무효화되어 기존 연결 프로그램에도 새 키를 입력해야 한다. 기존 키 원문은 다시 조회할 수 없으므로 분실 시 사용자가 재발급한다. 과거에 만료일을 지정한 키는 그 만료일을 유지하며 자동으로 무기한이 되지 않는다. 키를 채팅에 요청하거나 파일·로그에 저장하지 않는다. SSO를 우회하거나 키를 대신 발급하지 않는다.
4. `python scripts/publish_client.py prepare --artifact "배포.zip" --plan "작업폴더/publish-plan.json"`을 실행한다. 단일 MD는 `--metadata "등록.json"`을 함께 사용한다. URL·명령어는 artifact 없이 metadata에 mode와 해당 안내를 넣는다.
5. 결과의 `options`와 `missing`을 보고 실제 조직·업무 분류를 선택하도록 질문한다. 새 도구인지 기존 도구의 업데이트인지 요약한다. 같은 프로젝트의 저장된 도구 ID 또는 관리 가능한 동일 packageId가 하나면 새 버전으로 연결한다. 같은 이름만으로 업데이트하지 않는다. 후보가 여러 개면 사용자가 선택한 `--tool ID`로 다시 준비한다. 의도적으로 별도 신규 등록하는 경우에만 `--new`를 쓴다.
6. **게시 전 반드시 “전체 사용자가 상세 조회 가능” 또는 “조회 승인 필요”를 확인**한다. 이미 이번 요청에서 명시했다면 다시 묻지 않는다. 기존 도구의 업데이트도 현재 권한 설정을 보여주고 유지·변경 의사를 확인한다. 필요한 조직·업무 ID를 `--org-id`와 `--category-id`로 지정하여 준비안을 다시 생성한다. 누락된 설명은 실제 프로젝트 자료를 근거로 채우고 확인되지 않은 호환성·기능을 꾸미지 않는다.
7. 필요한 값이 채워지고 사용자의 공개 범위가 확인되면 `python scripts/publish_client.py publish --plan "작업폴더/publish-plan.json" --visibility public` 또는 `--visibility approval`을 실행한다. 사용자의 등록 요청과 범위 답변이 있으면 추가 게시 승인을 반복해서 요구하지 않는다.
8. 성공 응답의 도구 ID·배포 번호·조회 승인 여부를 알려준다. 준비안 옆 `.ai-square-publish-state.json`에 서버·사번·도구 연결이 저장되어 다음 업데이트에 사용된다. 준비안과 상태 파일은 배포 ZIP에 포함하지 않는다. 파일 내용이 바뀌면 prepare부터 다시 실행한다.

네트워크 응답이 끊기면 같은 준비안으로 재시도한다. `clientRequestId`로 이미 게시된 결과를 반환하여 같은 버전이 중복 생성되지 않는다. 409 버전 충돌은 최신 상세를 확인하고 다시 준비한다. 403은 업로드 키의 scope와 도구 관리 권한을 확인한다. 서버 오류에서 다른 사번이나 다른 도구로 우회하지 않는다.

등록 JSON에는 `name`, `desc`, `platform`, `type`, `guide`, `workTags`, 필요하면 `environment`, `changes`를 넣는다. 조직·업무는 플랫폼의 ID를 사용한다. 승인형은 목록까지 숨기는 기능이 아니라 상세 조회·다운로드를 제한하는 기능이다. 승인자 추가나 실제 데이터 접근 권한은 웹의 별도 권한 관리 절차를 따른다.

등록자 사번은 KEY에 연결된 사용자를 서버가 결정한다. SSO의 `emp_no`는 사번, `emp_name`은 이름, `dept`는 부서명, `dept_cd`는 부서코드이며 Skill이 별도로 수집하거나 패키지에 넣지 않는다. 자동 등록의 담당자 표시명(`owner`)은 인증된 사용자 이름이 기본값이다. 이 표시명을 바꿔도 실제 등록자·관리 권한·기여도 귀속은 바뀌지 않는다. 로그인 부서와 도구 분류용 조직은 별개이므로 `options`의 조직·업무 ID를 확인하여 선택한다. mock 환경에서도 설정한 사번으로 같은 등록 절차를 사용한다.

## 대상과 사용 방식 파악

기존 프로젝트의 안내 문서와 실행 진입점을 먼저 확인한다. 이미 있는 설정과 구조를 존중하고, 꼭 필요한 정보가 없을 때만 질문한다.

- 사용 프로그램은 Claude / ChatGPT / 기타 중 선택한다. 대상이 불명확하면 Claude가 맞는지 확인하되 실제 호환성을 임의로 확정하지 않는다.
- 실제 진입점과 사용 방식을 보고 공유 유형을 판단한다. MCP 서버 또는 독립 실행 도구는 `MCP/Tool`, 모델이 읽는 SKILL.md 중심의 지침과 보조 코드는 `Skill`, 호스트 플러그인 manifest·훅이나 실행 흐름을 묶은 패키지는 `플러그인/하네스`로 기록한다. 여러 유형이 섞이면 사용자가 설치하는 최상위 배포 단위로 분류하고 판단 근거를 설명한다. 불명확한 경우에만 묻는다. 확장자만으로 판단하지 않는다.
- 파일 설치, 터미널 명령어 설치, 원격 서버 연결, 웹 접속 중 실제 사용 방식을 확인한다. 웹은 ZIP 선언의 type을 읽어 자동 입력하며 소스 코드를 분석해 추론하는 것은 아니다.
- Skill에는 SKILL.md뿐 아니라 Python 코드, 참고 자료, 필요한 리소스가 포함될 수 있다.

## 기존 도구를 보존하며 배포 자료 준비

- 원본을 변경하지 않아도 되는 작업은 별도의 배포 폴더에서 수행한다. 기존 제품 동작을 바꾸는 수정은 요청 범위에 포함될 때만 한다.
- 여러 파일을 참조하는 Skill이나 소스 묶음은 ZIP으로 준비한다. 기존 상대 경로와 디렉터리 구조를 유지한다. 단일 Markdown만으로 동작하고 사용자가 MD 배포를 원하면 `.md` 원본으로 제공한다. 설명 파일을 추가하려고 억지로 ZIP으로 만들지 않는다. 설치 안내는 웹 입력용 텍스트로 별도 전달한다.
- 단일 MD는 `python scripts/prepare_package.py "원본/SKILL.md" "배포/SKILL.md"`로 원본 바이트를 보존해 복사할 수 있다. 웹에서 **파일 등록 → MD 선택**으로 게시한다. 이 경우 ZIP 선언 자동 입력 대신 유형 `Skill`과 설명을 직접 선택·입력한다.
- 명령어 배포는 ZIP 없이 **명령어 안내**로 등록한다. 실제 도구의 공식 CLI와 지원 범위를 확인하고 프로젝트용·사용자 전역용 명령어를 각각 준비한다. 추측한 CLI 옵션을 만들지 않는다. 지원하지 않는 범위는 비워 두고 이유를 설치 안내에 적는다. 사용자 비밀번호·토큰을 명령어에 포함하지 않는다.
- 원격 MCP와 웹앱은 URL과 인증·권한 안내를 준비한다. URL을 억지로 ZIP이나 EXE로 바꾸지 않는다.
- EXE·MSI·PS1이 이미 있으면 원래 용도와 실행 절차를 기록한다. 해당 도구가 없는 환경에서 설치 파일을 만들었다고 주장하지 않는다.
- 실행 파일이 필요하다는 이유만으로 NSIS 등 시스템 프로그램을 임의 설치하거나 관리자 권한을 요구하지 않는다. 빌드 도구가 없으면 가능한 배포 형식과 남은 작업을 명시한다.
- 사용자 토큰, .env, 비밀키, 개인 데이터, 로그, 개인 PC 절대 경로를 포함하지 않는다. 필요한 환경변수는 값 없는 예시로 설명한다.
- 원래 프로젝트의 의존성과 라이선스를 확인한다. 가상환경 전체를 복사하기보다 필요한 라이브러리와 설치 방법을 기록한다. 사내망에서 의존성을 받을 수 있는지도 구분한다.

## 등록 설명과 설치 안내

### 카드 소개와 동작 흐름

`desc`에는 동료가 카드만 보고 이해할 수 있는 기능 설명을 200자 이내로 작성한다. 입력 자료, 하는 일, 얻는 결과를 1~2문장으로 구체적으로 적고 태그를 반복해 나열하지 않는다.

실제 코드·SKILL.md·사용 안내에서 확인한 동작을 `workflow.steps`의 1~8개 단계로 정리한다. 각 단계는 `title`(필수, 60자)과 `description`(선택, 240자)으로 작성한다. 웹이 이 선언을 순서형 도식으로 표시하므로 HTML·Mermaid·스크립트를 생성하지 않는다. 검증되지 않은 처리·권한 검사·외부 연동을 단계에 추가하지 않는다. 흐름이 명확하지 않으면 확인하거나 생략한다. 구체적인 JSON 예시는 [배포 정보 규칙](references/package-format.md)의 동작 흐름 표시를 따른다.

ZIP은 ai-square.json에, 단일 MD·URL·명령어 자동 게시는 등록 metadata JSON에 workflow를 넣는다. 흐름을 넣기 위해 단일 MD를 ZIP으로 변환하지 않는다. 새 버전을 준비할 때 기존 흐름이 실제 변경 사항과 맞는지도 확인한다. 단일 MD·URL·명령어의 기존 흐름은 새 metadata에서 생략하면 유지하고, `workflow`를 지정하면 교체하며 `"workflow": null`이면 제거한다. 정상적으로 읽힌 ZIP 선언은 해당 버전의 기준이므로 흐름을 생략한 새 선언은 이전 흐름을 이어받지 않는다. 흐름 정보가 없는 기존 도구도 정상적으로 등록·사용할 수 있다. 웹 서버가 설명 문장을 임의로 해석해 만들어 내는 흐름은 아니다.

### 설치 범위는 항상 명시적으로 선택

생성하는 설치 프로그램은 **어떤 파일 복사·의존성 설치·설정 변경보다 먼저** `현재 디렉토리(프로젝트)` / `전역(내 계정)` 선택을 받아야 한다. 기본 선택은 두지 않는다. 빈 입력·입력 취소·비대화형 실행에서 전역으로 자동 전환하지 않는다. 비대화형 실행은 사용자가 명시한 scope가 있을 때만 진행한다. 지원하지 않는 범위를 선택하면 이유를 알리고 중단한다.

- Python 설치기는 `scripts/install_scope.py`의 `select_scope()`를 가져와 사용한다. 이 도우미는 선택한 범위·기준 경로만 반환한다. 실제 파일 설치는 호스트 규칙에 맞춰 작성한다.
- PowerShell 설치기는 `assets/SELECT_SCOPE.template.ps1`을 시작 부분에 반영한다. 다른 언어·EXE 생성 시에도 같은 선택·취소 동작을 구현한다. 기존 EXE가 선택을 지원하지 않으면 내부를 고쳤다고 주장하지 말고 해당 제약을 알린다.
- 프로젝트 경로는 설치 스크립트가 있는 폴더가 아니라 사용자가 터미널에서 열어 둔 작업 폴더 또는 명시한 프로젝트 경로다. 전역은 현재 사용자 홈 범위이며 모든 Windows 사용자나 관리자 권한 설치를 뜻하지 않는다. 쓰기 전에 실제 대상 경로를 보여준다.
- MD만 배포할 때는 실행 설치기가 없으므로 안내 첫 단계에 두 범위를 설명하고 사용자가 선택한 위치로 복사하도록 한다. 파일 자체가 대화창을 띄운다고 설명하지 않는다.
- URL 연결도 호스트에 범위 개념이 있으면 사용자가 선택하도록 안내한다. 범위 개념이 없는 서비스는 적용 불가와 이유를 명시한다.

빈 입력, 취소, 프로젝트 선택, 전역 선택을 검증하고 어느 경우에도 묵시적 전역 설치가 없는지 확인한다. 웹은 임의로 올린 EXE·PS1 내부의 선택 절차까지 강제할 수 없으므로 실제 설치기의 검증 여부를 구분해 인계한다.

관련 업무 태그를 등록자와 함께 정리한다. 넓은 업무 분야(제조·장비·기술)와 별개로, 실제 도움이 되는 업무명을 최대 8개, 각 30자 이내로 적는다. 예: 불량 분석, 수율 검토, 품질 회의. 사용자가 쓰는 업무 표현을 존중하고 지원하지 않는 업무를 검색 노출용으로 추가하지 않는다. 웹에서는 쉼표로 구분해 입력하며 도구 이름·설명과 함께 검색된다.

`assets/INSTALL_GUIDE.template.md`를 실제 도구에 맞게 채운다. 사용자 PC에서 설치하는 위치와 서버에서 실행하는 위치를 구분한다. 파일 생성·설정 변경 범위와 제거 방법을 구체적으로 적는다. 기존 사용자의 다른 도구나 개인 설정을 덮어쓰지 않는 방법을 우선한다.

파일 ZIP은 `assets/ai-square.example.json`을 실제 프로젝트에 맞춰 작성하여 ZIP 최상위에 `ai-square.json`으로 넣는다. 정확한 필드와 제약은 [배포 정보 규칙](references/package-format.md)을 따른다. 웹이 이 선언을 읽어 기본 정보·설치 안내를 자동 입력하고 시작 파일·필수 파일을 검사한다. 코드나 의존성을 실행하지 않으며 EXE로 변환하지 않는다. 기존 `assets/registration.example.json`은 수동 등록 참고 양식이며 ZIP 선언으로 사용하지 않는다.

공유할 파일만 있는 별도 폴더를 준비하고 `python scripts/prepare_package.py <준비폴더> <폴더밖의출력.zip>`으로 ZIP을 만든다. 경로에 공백이 있으면 따옴표로 감싼다. 스크립트가 참조하는 `package_contract.py`를 같은 scripts 폴더에 둔다. 원래 프로젝트 전체를 무조건 압축하지 않는다. 출력 ZIP은 웹의 **도구 등록 → ZIP에서 불러오기**로 확인한다. 이미 입력한 내용이 있으면 **ZIP 정보를 입력란에 적용**을 눌러 반영한다. 조직·업무 분야·담당자·조회 권한은 웹에서 직접 선택한다.

버전 번호는 웹에서 발급하도록 두고, 등록자는 바뀐 내용을 적는다. 업데이트·복구 지원 여부는 실제 구현을 확인한 범위에서만 설명한다. 웹의 배포 버전 변경과 사용자 PC의 설치 버전 변경은 다르다.

현재 웹의 실제 저장 모드에서는 **도구 등록 → 파일 업로드 → 게시**로 v1을 만들고, **등록 관리 → 버전 → 새 버전 등록**으로 v2를 게시한다. ZIP 내부 파일을 자동 설치하거나 EXE로 변환하지 않고 업로드 원본을 보관한다. 게시 시 선언을 다시 검사하고 MongoDB의 해당 버전에 보관한다. **배포 정보 JSON 받기**에는 도구 ID·배포 번호·원본 해시·버전 확인 주소가 들어간다. 이 파일은 원본 ZIP과 별도로 제공된다. 버전 복구는 웹에서 배포할 파일과 안내를 이전 버전으로 바꾸는 기능이다. 명시적인 dummy 모드는 조회 전용이므로 게시·저장이 불가능하다. 조직·업무는 웹의 현재 선택지에서 고르며, 승인형 도구도 목록은 공개되고 상세 조회만 승인 여부에 따라 제한된다.

ChatGPT 대상은 자료를 복사·첨부하는 방식과 원격 MCP 연결을 구분한다. 계정 정책이나 연결 기능을 확인하지 못했다면 '파일 활용 안내' 또는 '연결 조건 확인 필요'로 적는다. 로컬 플러그인을 곧바로 설치할 수 있다고 가정하지 않는다.

## 검증과 인계

### 실행 시 버전 확인 (파일 자동 교체 없음)

사용자가 실행 시 최신 버전 확인을 원하면 `scripts/version_check.py`와 `assets/VERSION_CHECK_GUIDE.md`를 참고해 실제 실행 진입점에 확인 코드를 연결한다. 서버 API는 `GET /api/tools/{toolId}/version-check?release={installedRelease}`이다. 현재 배포와 설치 버전이 다르면 새 버전 또는 서버 복구 안내를 보여주며 다운로드·설치·코드 교체는 하지 않는다.

도구 ID와 설치된 배포 번호는 해당 웹 게시 결과에서 가져온다. **설치 버전을 실행 시 서버 최신 번호로 덮어쓰면 안 된다.** 파일을 사용자가 실제로 교체했거나 설치를 마쳤을 때만 로컬 배포 번호를 갱신한다. 웹은 업로드 후 번호를 발급하므로 이 번호를 게시 전부터 알고 있다고 가정하지 않는다. 등록 후 ID·배포 번호를 설치 안내에 적고, 설치 과정에서 도구 외부의 로컬 설정에 기록하는 방식을 안내한다.

MCP는 시작 코드 또는 도구 호출 진입점, Python 기반 Skill은 실행 스크립트, 플러그인은 지원되는 실행 훅에 연결한다. Markdown 전용 Skill은 실행 훅이 없으므로 자동 확인을 보장하지 않는다. MCP 표준 출력에는 안내를 쓰지 않고 stderr 또는 호스트가 지원하는 알림을 사용한다. 서버 접근 실패와 최신 버전을 구분하며 기본 2초 네트워크 타임아웃을 둔다. 버전 확인 실패 자체로 기존 로컬 실행을 중단하지 않되, 원본 업무 시스템의 권한 검사는 그대로 유지한다.

운영 API에는 개인 연결 KEY와 도구 조회 권한이 필요하다. 버전 확인에는 **조회·다운로드** KEY면 충분하며 **업로드 포함** KEY도 사용할 수 있다. 실행 프로그램이 사용자의 KEY를 안전하게 읽어 `check_version(..., token=key)`에 전달한다. KEY를 코드·배포 ZIP에 넣지 않는다. 다른 인증 방식이 이미 있다면 `opener`를 사용할 수 있지만 `token`과 동시에 전달하지 않는다. Python 프로세스는 웹 브라우저의 SSO 로그인을 자동 공유하지 않는다. 401이면 `/local-access`에서 KEY 상태·재발급 여부를 확인하고, 403이면 도구 조회 권한을 확인한다. 버전 확인 실패 자체로 로컬 실행을 중단하지 않는다. mock은 설정한 사번으로 같은 API를 로컬에서 시험한다. 구체적인 예시는 [버전 확인 안내](assets/VERSION_CHECK_GUIDE.md)를 따른다.

가능한 범위에서 ZIP 내부 경로, 필요한 파일 누락, 의존성 설명, 비밀정보 포함 여부를 확인한다. 실행 검증은 격리된 예제 자료로 하고, 실제 사내 시스템 호출·계정 변경·PC 설치는 요청에 포함된 범위에서만 수행한다.

완료 시 다음을 짧게 제시한다.

1. 업로드할 파일, 등록할 URL 또는 범위별 설치 명령어. 단일 MD는 MD 그대로 제공한다.
2. 도구 이름, 한 줄 소개, 프로그램, 유형, 관련 업무 태그, 조직·담당자, 필요한 권한.
3. 동료가 따라 할 설치·연결 안내와 사용 예시.
4. 확인한 항목과 아직 확인하지 못한 항목.

보안 검사, 코드 서명, 자동 업데이트, 롤백을 검증하지 않았다면 완료했다고 표시하지 않는다. 기본 작업 범위는 웹에 올리기 전 자료 준비까지이다. 사용자가 게시까지 명시적으로 요청한 경우에도 실제 접속 가능한 플랫폼 도구와 권한을 확인하고 그 범위 안에서 처리한다.
